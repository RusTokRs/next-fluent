## 1. Метод

Девятнадцать проходов разобрали библиотеку по модулям и по слоям (V16 — слои
роутинга, V17 — `request-store`/`server-utils`/`domain-routing`/`plugin`,
V18 — чтение каталога и серверный вход, V19 — серверная конфигурация, RTL,
`prefetch`). Двадцатый прошёл по двум осям, которые раньше не использовались:

- **дифференциальный фаззинг** — один и тот же вход подаётся одновременно в два
  места, и сравниваются их ответы, а не каждый ответ по отдельности. Так
  проверялся маскер разбора (`usage.ts`), где «правильный» ответ заранее
  неизвестен, но известно, что два представления кода обязаны совпадать;
- **границы сериализации** — что именно библиотека обещает перенести через
  границу Server/Client Components, и что происходит с тем, что перенести
  нельзя.

Второй раз подряд часть работы — не находки, а **проверка собственных выводов
предыдущего отчёта**. В этот раз проверка дала не «подтверждено», а опровержение
(раздел 4), и это зафиксировано явно, потому что неверная пометка
«недостижимо» — самый надёжный способ похоронить хвост покрытия.

## 3. V20-01. Функции не переходят границу — и библиотека об этом молчала

`RequestConfigResult.functions` — единственный способ добавить в Fluent
собственную функцию (`BRL()`, `CARD()`, доменный формат). Сервер их подхватывает:
`src/server.ts:448` раскладывает конфиг, а строка 458 подмешивает
`...config.functions` в `bundleOptions`.

`src/server-provider.ts` переносит через границу всё, что сериализуется —
сообщения, фолбэки, `now`, `timeZone`, дефолтные функции, `direction`. Функции из
конфига **не сериализуются в принципе**, и провайдер их не передаёт. Это
правильно; неправильно то, что об этом не было ни слова.

Измерено на одной и той же таблице `price = { BRL($amount) }`:

```
сервер  (getTranslations → t('price'))   "R$ 1234.50"
клиент  (FluentProvider + useTranslations)  <span>price</span>
        console.error: ReferenceError: Unknown function: BRL()
```

То есть на одной странице один и тот же ключ даёт сумму в серверной части и свою
собственную строку в клиентской. `console.error` говорит, *что* не найдено, но
не *почему*: на сервере функция была. И `FluentServerProvider` — тот компонент,
который обязан это знать, — молчал.

Отдельно: **опция `functions` в request-конфиге не была документирована вообще.**
В README граница упоминалась одной фразой в разделе про корневой layout
(«функции надо регистрировать в Client Component»), но ни примера, ни связи с
конфигом, ни описания симптома не было.

**Исправление.** `FluentServerProvider` в development предупреждает, называя
каждую функцию, которую пришлось отбросить, и указывая решение:

```
[next-fluent] The request config defines Fluent functions "BRL", "USD", which
cannot cross the Server Component boundary. Messages that call them will not
format in Client Components. Define them on a `<FluentProvider functions={…}>`
inside a `'use client'` wrapper as well.
```

В production ветка недостижима, как и остальные диагностики провайдера. В README
добавлен раздел «Custom Fluent functions» с примером обеих сторон и объяснением,
почему функции держат в общем модуле.

**Почему не «просто передать».** Соблазнительное решение — пробросить `functions`
в `FluentProvider` — невозможно: RSC-сериализатор не переносит функции, и
попытка либо уронит рендер, либо тихо подменит функцию на `null`. Тест № 4
закрепляет это как конструкцию, а не как недосмотр: `'functions' in props === false`,
а всё сериализуемое (локаль, сообщения) переходит как раньше.

**Диагностика, а не исправление, — здесь потолок.** Библиотека не может знать,
какие функции нужны клиентской части, и не может их туда доставить. Всё, что в
её силах, — назвать потерянное там, где это ещё можно исправить.

## 4. V20-03. Отчёт V19 ошибся про `navigation.js`

В разделе 7 отчёта V19 написано:

> `navigation.js` (71.11 % веток): непокрытые ветки — `AppRouterContext` и
> `PathnameContext`, достижимые только внутри App Router.

Проверка показала, что это неверно. Непокрытыми оставались строки 95, 98 и 101
`dist/navigation.js`:

```js
  back()      { getRouter().back(); },
  forward()   { getRouter().forward(); },
  refresh()   { getRouter().refresh(); }
```

Это однострочные делегирования, и харнесс со стаб-роутером, написанный ещё в
V16, рендерит `useRouter()` вне App Router без всяких затруднений. Тесты № 6–7
покрывают все три и заодно закрепляют, что аргументы не добавляются и не
передаются.

```
dist/navigation.js   строки 97.18 → 100.00,  функции 81.25 → 100.00
```

**Вывод для процесса.** Пометка «достижимо только в среде X» удобна тем, что
снимает вопрос, и именно поэтому её надо проверять: из четырёх непокрытых веток
три оказались однострочниками. Правило для следующих проходов — прежде чем
писать «недостижимо», назвать конкретную строку и причину, по которой её нельзя
вызвать.

## 5. V20-04. Маскер разбора под дифференциальным фаззингом

`src/usage.ts` ищет вызовы переводов статически, без AST-парсера: сначала
`maskNonCode` вычищает строки, шаблоны, регулярки и комментарии (заменяя их
пробелами той же длины, чтобы не сдвинуть номера строк), потом по маске
собираются места вызова.

Конструкция держалась девятнадцать проходов на нескольких примерах. Проверка:
15 видов не-кода (однострочный и блочный комментарий, JSDoc, три вида кавычек,
шаблон, выражение внутри шаблона, регулярка, экранированная кавычка,
экранированный бэктик, деление, похожее на регулярку) подавались во все шесть
форм вызова (`t`, `t.raw`, `t.rich`, `t.attrs`, `t.plain`, `t.has`) в количестве
от 1 до 15 блоков сразу — 90 случаев на сдвиг номера строки, 15 случаев на
утечку ключа из не-кода, 1 случай на то, что `${…}` внутри шаблона остаётся
видимым кодом.

```
106 случаев, 0 отказов
```

Номера строк совпадают с ожидаемыми во всех 90; ни один ключ из комментария,
строки, шаблона или регулярки не попал в отчёт ни в одном из 15; вызов внутри
`${…}` собирается, как и должен.

Это **отрицательный результат, и он стоит того, чтобы его закрепить**: теперь
фаззинг — постоянный гейт (`audit-v20` № 8–10), а не разовая проверка. Правка
маскера, которая сдвинет нумерацию или начнёт видеть ключи в комментариях,
уронит тест, а не пройдёт мимо.

## 6. V20-02. Псевдолокали: почему вопрос нельзя закрыть кодом

`readCatalogsByLocale` выводит локаль из первого сегмента пути. Каталог
`messages/shared/en.ftl` — обычная раскладка для переиспользуемых сообщений —
даёт псевдолокаль `shared`, которая попадает в `check` и даёт ложные
расхождения с эталоном. V18 и V19 откладывали вопрос как «решение владельца».

Попытка закрыть его предупреждением упирается в измерение:

```
canonicalizeLocale('shared')      → "shared"
canonicalizeLocale('common')      → "common"
canonicalizeLocale('app')         → "app"
canonicalizeLocale('admin')       → "admin"
canonicalizeLocale('ui')          → "ui"
canonicalizeLocale('web')         → "web"
canonicalizeLocale('components')  → undefined
canonicalizeLocale('marketing')   → undefined
```

Подтег языка в BCP-47 — 2–3 либо 5–8 букв, поэтому ровно те имена, которые
реально дают каталогам-пространствам имён, являются корректными тегами.
Отличить `messages/shared/` от гипотетической `messages/xyz/` синтаксически
нельзя. Эвристика вроде «предупреждать, если имя не в списке локалей» требует
самого списка, а `check` его не получает — он locales и обнаруживает.

**Решение.** Вопрос закрыт как неразрешимый в коде, а не отложен в
двадцатый раз: тест № 5 закрепляет измерение, чтобы следующий проход не
изобретал ту же эвристику заново. Практический совет владельцам каталогов —
держать переиспользуемые сообщения внутри каталога локали
(`messages/en/shared.ftl`), что даёт тот же импорт `shared/greeting` без
псевдолокали; это уже описано в README в разделе про каталоги.

## 8. Бюджет размера

`src/server-provider.ts` не входит в `CLIENT_ENTRIES`
(`src/index.ts`, `src/index-browser.ts`, `src/middleware.ts`), как и
`src/server.ts`, поэтому диагностика в клиентский бюджет не попадает:

```
npm run size → "Size budgets respected."
```

Потолок собственного кода, поднятый в V19 до `40.25 * 1024`, не менялся.

## 9. Приоритеты на двадцать первый проход

Проверенных гипотез за двадцать проходов накопилось больше, чем осталось
нетронутых модулей. Честный список того, что ещё не закрыто:

1. **`server.js` 84.73 % строк.** Хвост разобран в V19 и состоит из двух частей,
   обе измерены: `getLocale` в объёме запроса (тестируется только через Next
   fixture) и `resolveConfigFn` (ветка `!missingAlias` недостижима вне Next.js —
   у пакета нет экспорта `./config`, поэтому динамический импорт всегда бросает
   `ERR_PACKAGE_PATH_NOT_EXPORTED`). Это потолок, а не задача.
2. **Скрипт покрытия.** `npm test` его не считает, цифры в отчётах — ad-hoc.
   `npm run coverage` снял бы расхождение между «что мы думаем» и «что меряется».
3. **Оставшиеся необследованные модули.** `alternate-links.ts` (138 строк),
   `factory.ts` (112), `lru.ts` (52), `ftl-parse.ts` (75) читаны мельче прочих;
   `catalog-integrity.ts` прочитан в этом проходе — дефектов нет, проверки
   корректные и задедуплицированные.
4. **Границы сериализации, кроме функций.** V20-01 нашёл одну. Тот же вопрос
   стоит задать про `onError`, `getMessageFallback`, `richValues` с колбэками и
   `useIsolating` — что из них переходит, что теряется и что при этом
   диагностируется.
5. **Дифференциальный фаззинг на других парax.** Приём V20-04 обобщается:
   `readCatalogsByLocale` против `loadMessages`, `buildLocalizeUrl` против
   `matchLocalePrefix`, `parseFtl` против `createFluentBundle`.
