## P1 — дефекты с неверным результатом

### V3-01. Булевы аргументы молча выбрасывались → вместо текста ключ

**Место:** `src/bundle.ts` (`buildFluentArgs`).

`buildFluentArgs` пропускал только `string | number | Date | {'type' in v}`. `boolean` не входил в список, переменная не попадала в `FluentArgs`, `@fluent/bundle` фиксировал `ReferenceError: Unknown variable`, а `formatCandidate` трактовал это как `FORMAT_ERROR` и возвращал ключ.

Воспроизведение (до правки):

```
ftl: bool-msg = Admin: { $isAdmin }
t('bool-msg', { isAdmin: true }) → "bool-msg"          // вместо "Admin: true"
t.raw('bool-msg', { isAdmin: false }) → "Admin: {$isAdmin}"
console: ReferenceError: Unknown variable: $isAdmin
```

`@fluent/bundle` 0.19 действительно не поддерживает `boolean` (`resolver.js`: `switch (typeof arg)` → `string | number | object` → иначе `TypeError`), поэтому «пропуск» выглядел защитой, но цена — потеря целого сообщения.

**Исправление.** `boolean` → `String(v)`, `bigint` → `Number(v)`; `null`/`undefined` и не-Fluent объекты собираются в список `rejected` и сообщаются как `INVALID_ARGUMENT` **только если сообщение реально не отформатировалось** (иначе лишний шум на неиспользуемых аргументах).

После: `t('bool-msg', { isAdmin: true })` → `Admin: true`; `t('big', { total: 10n })` → `Total: 10`.
Тесты: `test/audit-v3.test.mjs` («V3-01»).

### V3-02. Заголовок `x-next-fluent-rewrite` подделывался клиентом → 404 на валидном URL

**Место:** `src/middleware.ts` (ранний выход по сигнальному заголовку).

Middleware проверял `request.headers.get('x-next-fluent-rewrite') === rawPathname` и в этом случае **полностью пропускал** канонизацию и внутренний rewrite. Заголовок приходит из запроса, то есть управляется клиентом.

Воспроизведение (до правки), `as-needed`, `pathnames: { '/about': { en: '/about-us', ru: '/o-nas' } }`:

```
GET /ru/o-nas                                   → 200, x-middleware-rewrite: /ru/about   (ок)
GET /ru/o-nas + x-next-fluent-rewrite: /ru/o-nas → 200, x-middleware-next: 1, БЕЗ rewrite
   ⇒ приложение получает /ru/o-nas, маршрута app/[locale]/o-nas нет ⇒ 404
GET /ru/o-nas (localePrefix: 'always') + тот же заголовок → тоже без rewrite ⇒ 404
```

Это не только «сам себе 404»: ответ 404 на валидном локализованном URL может быть закеширован общим кешем/CDN и отдан всем пользователям.

**Почему заголовок вообще существует (проверено, а не по документации).** В Next.js 15.5.26 middleware вызывается **дважды** на запрос: после `NextResponse.rewrite()` он повторно отрабатывает по внутреннему пути. Счётчик в фикстуре: `x-mw-calls: 2` для `GET /`, `x-mw-path: /en`; 5 → `/ru/about`. Без сигнала второй проход канонизирует собственный rewrite-таргет обратно (в `as-needed` для дефолтной локали и в `never` — бесконечный редирект).

**Исправление.** Сигнал учитывается **только в тех двух ветках, где возможен цикл** (`localePrefix: 'never'` и `as-needed` + префикс дефолтной локали). В `always` и в `as-needed` для недефолтной локали второй проход идемпотентен, поэтому заголовок там игнорируется полностью. Дополнительно клиентский заголовок вычищается из проксируемых заголовков (`requestHeaders.delete(...)`), а при rewrite заменяется нашим значением.

После: оба кейса выше дают `x-middleware-rewrite: /ru/about`; защита от цикла сохранена (тест «V3-02: the signal still prevents the as-needed default-locale redirect loop»).
Тесты: `test/audit-v3.test.mjs` (3 теста «V3-02»).

## P2 — архитектура, производительность, семантика

### V3-03. `localePrefix` / `cookieName` / `headerName` не валидировались

`validateI18nConfig` принимал любые значения. Опечатка `localePrefix: 'as-neede'` (или `'AS-NEEDED'`) молча давала поведение `'always'` — и в middleware, и в генерации href; `cookieName` с CRLF принимался и падал позже на `Headers.set`.

```
defineRouting({ locales:['en','ru'], defaultLocale:'en', localePrefix:'as-neede' }) → принято
defineRouting({ ..., cookieName: 'bad\r\nname' })                                   → принято
```

**Исправление:** whitelist режимов и проверка имён cookie/заголовка по RFC 6265/9110 token-грамматике; ошибка на этапе конфигурации. Тест «V3-03».

### V3-04. `Set-Cookie` на каждый ответ middleware → статические страницы нельзя кешировать

До правки `createSuccessResponse` и `createRedirect` **безусловно** ставили `NEXT_LOCALE` (`git show HEAD:src/middleware.ts`, строки 148–154 и 167–173). Следствия: перезапись выбора пользователя на каждом запросе, включая подгрузки RSC/изображения, и `Set-Cookie` в ответе на пререндеренную страницу (общий кеш такой ответ не переиспользует).

Для сравнения прочитан `next-intl@4.14.7` (`middleware/syncCookie.js`): cookie пишется только для `sec-fetch-dest === 'document'`, только если значение отличается, и не пишется, если cookie нет, а `Accept-Language` и так даёт эту локаль.

**Исправление:** та же логика + опция `localeCookie`. Измерено на production-приложении после правки:

```
GET /ru/o-nas (cookie NEXT_LOCALE=ru, document) → 200, Set-Cookie: <нет>, cache-control: s-maxage=31536000
GET /ru/o-nas (без cookie)                      → 200, Set-Cookie: NEXT_LOCALE=ru
GET /ru/o-nas (sec-fetch-dest: image)           → 200, Set-Cookie: <нет>
```

Тесты «V3-04» + проверка в `scripts/test-next-integration.mjs`.

### V3-05. Cookie не настраивалась и не имела `Secure`

Не было ни имени, ни атрибутов. **Исправление:** `localeCookie: false | { name, maxAge, sameSite, secure, domain, path, httpOnly, partitioned, priority }`, дефолт совместим с предыдущим поведением (`NEXT_LOCALE`, `maxAge=31536000`, `sameSite=lax`, `path=/`). `Secure` намеренно **не** включается автоматически (как в next-intl): молча потерянная cookie на HTTP-деплое хуже явной опции — она документирована в README. Тест «V3-05».

### V3-06. Слаг другой локали давал 404 вместо внутреннего маршрута

`internalPath()` в middleware сопоставлял только шаблоны текущей локали, тогда как навигация (`localizePath`) перебирает все. Асимметрия:

```
GET /ru/about-us → 200 без rewrite ⇒ 404 (app/[locale]/about ожидает /ru/about)
```

**Исправление:** middleware резолвит внешний слаг по всем локалям (как `usePathname`). После: `GET /ru/about-us` → `x-middleware-rewrite: /ru/about`. Тест «V3-06».

### V3-07. `createI18n().getFormatter()` игнорировал `timeZone` из request config

`factory.getFormatter` создавал форматтер напрямую, минуя снапшот запроса, — даты рендерились в часовой зоне сервера, тогда как `next-fluent/server.getFormatter` её учитывал.

```
requestConfig: { timeZone: 'UTC' } → runtime.getFormatter({locale:'en'}).timeZone === undefined
```

**Исправление:** фабрика делегирует в серверный `getFormatter` (и в `getMessages` — раньше при отсутствии `loadMessages` возвращался `''`, игнорируя `setRequestConfig`). Тест «V3-07» (`Asia/Tokyo` → `'09'` для полуночи UTC).

### V3-08. `t.raw()` сортировал атрибуты по алфавиту

Для сообщения только с атрибутами значения возвращались отсортированными, то есть отвязанными от имён атрибутов:

```
login-button =
    .label = Sign in { $name }
    .aria  = Sign in as { $name }
t.raw('login-button') → ["Sign in as {$name}", "Sign in {$name}"]   // aria раньше label
```

**Исправление:** порядок объявления из каталога. Существующий тест, закреплявший алфавитный порядок, обновлён с комментарием (N03 в `review-regressions.test.mjs`).

### V3-09. Биди-изоляторы протекали в `<title>`, meta и JSON; `useIsolating` был недоступен

Fluent по умолчанию вставляет U+2068/U+2069 вокруг плейсхолдеров. `t()` их сохранял, `t.raw()` — вырезал (несогласованно), а отключить через публичный API было нельзя: `createFluentBundle` опцию принимал, но `getTranslations`/request config/`FluentProvider` её не прокидывали.

```
t('title', { count: 3 }) → "Dashboard ⁨3⁩"   // невидимые символы в <title>/JSON
t.raw('title', { count: 3 }) → "Dashboard 3"
```

**Исправление:** `useIsolating` в `RequestConfigResult`, `GetTranslationsOptions`/`ForLocaleOptions` и `FluentProviderProps`; режим входит в ключ кеша бандлов (и глобального, и request-scoped), иначе один кеш отдавал бы бандлы с разным форматом. Тест «V3-09».

### V3-12. `setRequestLocale` тихо не работал вне request scope, а документированная настройка не давала статического рендеринга

`getRequestStore` — это `React.cache()`. Без активного async-диспетчера React не кеширует ничего, поэтому вне рендера каждый вызов создаёт новый store:

```
setRequestLocale('ru', ['en','ru']); await getLocale() → 'en'
getNow() === getNow()                                  → false
```

Хуже другое. В production-сборке фикстуры все локализованные маршруты были `ƒ (Dynamic)`, а `prerender-manifest.json` содержал только `/_not-found`. Причина (измерено пробной страницей):

```
[probe] store stable: true  store.locale: undefined   // setRequestLocale из layout не дошёл до page
[probe] getLocale(): en                               // обе локали пререндерились бы как en
```

Next.js рендерит layout и page независимо, поэтому `setRequestLocale` обязателен **в каждой странице и каждом layout** — то же требование documented у next-intl, но в README next-fluent был показан только layout.

**Исправление.** Фикстура переведена на корректную схему (`generateStaticParams` + `setRequestLocale` в layout и в обеих страницах), а `scripts/test-next-integration.mjs` теперь читает `prerender-manifest.json` и падает, если `/en`, `/ru`, `/en/about`, `/ru/about` не пререндерены (таблица маршрутов в выводе `next build` при этом врёт: `/[locale]/live` с `headers()` показан как `●`, но в манифесте отсутствует — поэтому проверяется именно манифест). README дополнен разделом «Static rendering».

```
[next-fluent] Static rendering verified for: /en, /ru, /en/about, /ru/about
```

Последний пункт стоит пояснить. У next-intl экстрактор существует потому, что
источник истины там — код, а JSON-каталог это поддерживаемая вручную тень.
Генерировать каталог из вызовов для Fluent нельзя без потерь: вызов
`t('items-count')` не несёт информации о селекторах, атрибутах, терминах и
комментариях переводчику, а пустой авто-ключ хуже отсутствующего — `check` счёл
бы локаль полной, а UI молча отрендерил имя ключа. Поэтому реализовано обратное
направление: `analyzeUsage()` сравнивает каталог с call sites и сообщает
`unused` (мёртвые ключи), `dynamic` (непроверяемые статически вызовы), `missing`
и `missing-attributes`. Каталог при этом никогда не перезаписывается.

`generateTypeDeclarations` больше не экспортируются из корневого entry — они
тянут за собой полный FTL-парсер, который браузеру не нужен.

## Второй проход: adversarial-проверка

Повторная проверка «не доверяй своему же отчёту»: каждый публичный вход
(middleware, JSON-каталоги, CLI, конфигурация роутинга) прогнан через набор
враждебных входов — протокол-относительные пути, инъекция `Host`/cookie,
`__proto__`, управляющие символы, мусорный `Accept-Language`. Найдено и закрыто
пять дефектов, каждый закреплён тестом в `test/hardening.test.mjs`.

| # | Дефект | Воспроизведение | Исправление |
| --- | --- | --- | --- |
| 1 | **Открытый редирект** | `localePrefix: 'never'` + `GET /ru//evil.example/x` → `307 Location: http://evil.example/x`. То же для `\` вместо `/` и для `as-needed` с префиксом дефолтной локали | `normalizeLeadingSlashes()` схлопывает ведущий набор `/` и `\` в каждом пути, производном от запроса; `requestUrl()` дополнительно сверяет `origin` цели и отказывается уходить на чужой |
| 2 | **Traversal в префиксах** | `localePrefix: { prefixes: { ru: '/../evil' } }` принимался конфигурацией | `validateLocalePrefix` отклоняет сегменты `.` и `..` |
| 3 | **Падение CLI** | файл `__proto__.ftl` → `TypeError: catalogs[locale].push is not a function` | карты локалей создаются с `Object.create(null)` |
| 4 | **Потеря сообщения из JSON-каталога** | `{"e": "value\r\nmore"}` → у `e` внутри литерала оставался «сырой» CR, рантайм-парсер отбрасывал запись целиком (Fluent не поддерживает `\u{…}`) | `renderFluentPattern` нормализует CRLF/CR в LF — значение становится валидным многострочным паттерном |
| 5 | **`next build` зависал** | плагин с `typegen` открывал рекурсивный `fs.watch`, который держит event loop даже после `unref()` (Linux, Node 22) | в production watcher не стартует, в dev — поллинг по unref-таймеру |

Проверено и признано безопасным (тесты добавлены как постоянная защита):
инъекция сообщений через значения JSON-каталога (`\n`, `    .attr =`, `#`,
`-term` остаются текстом), `__proto__` в JSON/`checkCatalogs`/`pickMessages`
(`Object.prototype` не трогается), недоверенный `x-forwarded-host` игнорируется,
чужой `Host` при `trustedHosts` даёт 421, CRLF в значении cookie не приводит к
инъекции заголовка, враждебный `setRequestLocale` отклоняется, `Accept-Language`
из 20 000 записей разбирается без деградации.

## Предельные нагрузки и производительность

Замеры на Node 22, не синтетические сценарии, а точки, где деградация видна
пользователю.

**Каталог.** Создание бандла: 1 000 ключей — 4.9 мс (cold) / 0.1 мс (warm);
10 000 — 31.3 / 0.5 мс; 50 000 — 124.5 / 4.3 мс, heap 61 МБ. Форматирование:
100 000 вызовов `t()` по каталогу на 50 000 ключей — 117 мс, ~1.2 мкс на вызов,
~0.85 млн вызовов/с. Usage-анализ: 200 файлов × 250 вызовов (50 000 сайтов)
против каталога на 50 000 ключей — ~285 мс.

**Локали.** Здесь нашлись две реальные деградации, обе закрыты.

| замер | было | стало |
| --- | --- | --- |
| `matchSupportedLocale`, последняя из 184 локалей | 113.2 мкс | **14.4 мкс** |
| `matchSupportedLocale`, первая из 184 | 29.3 мкс | **5.9 мкс** |
| тот же вызов на невалидном теге | ~113 мкс | **0.1 мкс** (отрицательный кэш) |
| middleware, 200 локалей | 3.498 мс/запрос | **2.187 мс/запрос** |
| middleware, 2 локали | — | 0.071 мс/запрос |

Причина первой: `Intl.getCanonicalLocales` вызывался заново для каждой
настроенной локали на каждом кандидате, а разрешение локали делает это
несколько раз за запрос. Кэш ограничен 500 записями и хранит в том числе
отрицательные результаты — заодно это снимает возможность дорогого повторного
разбора мусора из куки.

Причина второй: `matchLocalePrefix` пересобирал и сортировал таблицу префиксов
на каждом вызове, хотя она зависит только от списка локалей и конфига. Таблица
мемоизируется в `WeakMap` по идентичности обоих, поэтому живёт ровно столько,
сколько конфиг. Чтобы это было безопасно, `defineRouting` теперь делает
снимок списка локалей и замораживает его — `readonly` из сигнатуры стал
истинным и в рантайме.

Остаток в 2.187 мс разложен: 0.811 мс без hreflang и 2.187 мс с ним, то есть
~1.4 мс — это построение заголовка на 200 записей. Стоимость пропорциональна
размеру вывода, а не дефект; реалистичный сайт на 2 локали обслуживается за
71 мкс.

**Кэш бандлов.** 200 бандлов на 50 уникальных локалях — 1.2 мс, ~6 мкс на бандл.

Две мои ошибки в probe: синтетические локали `l0`/`l2` — невалидные BCP-47, и
`defineRouting` их справедливо отверг; и я снова ожидал, что
`matchLocalePrefix('/en/about', …, 'as-needed')` вернёт `null`, хотя функция
намеренно не зависит от режима — она сообщает о наличии префикса, а решение
принимает middleware.

## Установка и потребление: контракт пакета

Все предыдущие проходы проверяли библиотеку **изнутри репозитория**: тесты
импортируют `dist/*.js` по относительным путям, интеграция с Next запускается
в приложении внутри репо. Ни один из них не отвечал на вопрос, может ли
сторонний проект пакет установить и использовать — это решают только `exports`,
состав `files` и опубликованные типы.

**Найденный дефект (критичный для установки).** Пакет был ESM-only, а
`next.config.js` в большинстве приложений — CommonJS. То есть конфиг, который
документация предписывает обернуть плагином, не мог его загрузить:

| Node | поведение до фикса |
| --- | --- |
| < 22.12 | `ERR_REQUIRE_ESM` — `require()` от ESM запрещён |
| >= 22.12 | возвращается **namespace**, поэтому `createNextFluentPlugin(...)` → «is not a function» |

Второй случай хуже первого: ошибка выглядит как баг в коде пользователя, а не
как несовместимость формата.

Исправление повторяет решение next-intl, у которого CJS-условие `require` есть
ровно у одной точки входа — `./plugin`:

- `dist/cjs/*.cjs` — транспиляция замыкания плагина (6 модулей: `plugin`,
  `catalog-io`, `catalog`, `typegen`, `ftl-parse`, `errors`), без бандлинга, как
  и остальная сборка;
- `module.exports = Object.assign(module.exports.default, module.exports)` —
  модуль **сам** является фабрикой; `.default` и именованный экспорт сохранены
  для interop. Читать надо именно `module.exports`: esbuild уже переприсвоил его,
  а связка `exports` продолжает указывать на прежний пустой объект;
- `plugin.d.cts` с `export =`, чтобы `import x = require('next-fluent/plugin')`
  типизировался;
- точки входа приложения остались ESM-only — плагин работает в процессе конфига
  Node, это отдельный realm, поэтому разделяемое состояние не дублируется.

Две ловушки по пути, обе пойманы сборкой, а не на глаз:

1. `src/plugin.ts` строит `require` через `createRequire(import.meta.url)`. В CJS
   `import.meta` нет, esbuild эмитит `const import_meta = {}`, и плагин падал бы
   на `createRequire(undefined)` при загрузке. `define` у esbuild принимает
   только литералы, поэтому заглушка заменяется пост-обработкой на
   `pathToFileURL(__filename).href`; если esbuild когда-нибудь поменяет форму
   заглушки, сборка упадёт, а не соберёт сломанный файл.
2. Первый вариант `plugin.d.cts` был написан через `import type` — это
   реэкспорт **типа**, и вызов падал с TS1361. Поймал новый consumer-тест, а не
   ревью.

**Проверено и дефектов не найдено.** Все 9 путей импорта из README резолвятся
картой `exports`. `sideEffects: false` оправдан: `globalThis` в `src/` не
встречается ни разу, побочных эффектов при импорте нет. `size-budget` считает от
`src/`, поэтому CJS-сборка на клиентский бюджет не влияет. `next/link.js` и
`next/navigation.js` с расширением резолвятся: у Next 15.5.26 поля `exports` нет
вообще. Отсутствие алиаса `next-fluent/config` обрабатывается штатно —
`resolveConfigFn` возвращает `null`, а не падает. `files` полон, `LICENSE` на
месте, `npm pack` — 101 файл.

**Новый тест.** `npm run test:consumer` (включён в `npm run ci`) собирает
одноразовый потребитель и проверяет: резолвинг и состав экспортов всех 18 точек
входа; что каждый bare-импорт в `dist/` объявлен в зависимостях (кроме
виртуального `next-fluent/config`); что `next.config.js` и `next.config.mjs`
дают рабочий конфиг, причём алиас указывает внутрь **потребителя**, а не репо;
что `.mts` и `.cts` типизируются при `module: nodenext`. Отрицательный контроль
подтверждает, что проверка типов вообще способна упасть.

**Про `engines.node` — предыдущая рекомендация была неверной.** В прошлом проходе
я предложил расширить диапазон до Node 20, потому что Node-22-only API в коде не
нашлось. Это неверно по фактам: **Node 20 достиг end-of-life 30 апреля 2026** и
больше не получает исправлений безопасности, а Vercel отключает его для новых
сборок с 1 октября 2026. То есть `">=22.0.0"` — не избыточное ограничение, а
ровно правильный пол: 22 — старшая LTS, которая ещё поддерживается (до
30.04.2027). Расширять вниз означало бы поддерживать runtime без патчей;
поднимать до 24 — отсекать приложения на 22, не получая ничего взамен, потому что
ни один Node-24-only API в библиотеке не используется.

## Политика версий: где проходит граница легаси

Вопрос «поднять минимумы или сохранить широкий диапазон» проверялся фактами, а не
предпочтением.

**Что оказалось легаси на самом деле.** Версионно-зависимого кода в библиотеке
было ровно одно место: `needsLegacyTurboConfig()` в `src/plugin.ts` — чтение
`next/package.json` и парсинг версии на каждое вычисление конфига, чтобы для
Next < 15.3 положить алиас в `experimental.turbo` вместо top-level `turbopack`.
В рантайме приложения (middleware, server, client, navigation) версионных веток
нет вовсе — проверено грепом по `process.versions`, `semver`, feature-детекции.
Значит, цена поддержки Next 15 — не «легаси-реализация», а восемь строк в плагине.

**Решение.** Пол — самая старая версия, которая ещё получает обновления, а не
самая новая из доступных:

| | было | стало | обоснование |
| --- | --- | --- | --- |
| `engines.node` | `>=22.0.0` | `>=22.0.0` (без изменений) | Node 20 EOL 30.04.2026; 22 поддерживается до 30.04.2027 |
| `peerDependencies.next` | `>=15.0.0 <17.0.0` | **`>=15.3.0 <17.0.0`** | 15.3 — появление top-level `turbopack`; ветка для 15.0–15.2 удалена |
| `peerDependencies.react` | `>=19.0.0` | `>=19.0.0` (без изменений) | Next 16 требует 19.2, но 19.0+ остаётся валидным диапазоном |

Побочный эффект: `createRequire(import.meta.url)` и `readFileSync` из плагина
ушли — вместе с ними исчез и единственный повод для шима `import.meta` в CJS-сборке
(шим оставлен: он защищает будущие использования).

**Что важнее подъёма минимумов: Next 16 вообще не тестировался.** В репозитории
установлен Next 15, поэтому ветка харнесса, переименовывающая `middleware.ts` в
`proxy.ts`, не выполнялась ни разу, и Turbopack — дефолтный бандлер `next build`
начиная с 16 — не проверялся совсем. Добавлен `npm run test:next:16`
(`NEXT_FLUENT_NEXT_VERSION` ставит другую мажорную версию в одноразовое
приложение), включён в `npm run check`.

Прогон того же фикстура на **Next 16.3.6**: сборка под Turbopack прошла при
присутствии `webpack`-хука плагина; `proxy.ts` зарегистрирован как
«ƒ Proxy (Middleware)»; статика для `/en`, `/ru`, `/en/about`, `/ru/about`;
рантайм-проверки редиректов, hreflang и кук прошли. То есть библиотека уже
совместима с 16 — это просто не было проверено.

**Отдельно: гипотеза про webpack не подтвердилась.** Документация Next 16
утверждает, что при наличии кастомного `webpack`-конфига `next build` (теперь
Turbopack) **падает**. Проверено на живом 16.3.6: сборка прошла без ошибки и без
предупреждения, причём дважды. Плагин всё равно выставляет и `webpack`, и
`turbopack.resolveAlias`, так что алиас `next-fluent/config` работает при любом
бандлере; менять поведение по версии не потребовалось.

**Проверено и совместимо.** `headers()` и `cookies()` в `src/server.ts` уже
вызываются с `await` — требование Next 16, где синхронный доступ удалён
окончательно. TypeScript 6.0.3 в dev-зависимостях выше требуемого Next 16 минимума
5.1. `next lint` в Next 16 удалён — у нас используется `eslint` напрямую.

## Next.js 16: две несовместимости, найденные только матрицей CI

Заявленная поддержка обоих мажоров требовала реальной проверки. Матрица
(Node 22/24 × Next 15/16 × Ubuntu/Windows) существовала и раньше, но **на этой
ветке не запускалась ни разу** — триггер только на `main`. Открытый PR запустил
её впервые: 7 ячеек зелёные, одна красная — `ubuntu / Node 22 / Next 16`,
единственная, где включён браузерный прогон (Playwright). Два перезапуска дали
тот же результат, значит, сбой детерминированный.

Логи CI из этой среды недостижимы (blob-хранилище недоступно), поэтому вывод
интеграционного прогона теперь дублируется в аннотации check-run — и это
сработало: сообщение показало, что после клика на «Switch to English» браузер
оказался на `/ru/o-nas` вместо `/about-us`.

### Дефект 1: бесконечный цикл редиректов на Next 16

Next 15 держит rewrite из middleware прозрачным. Next 16 отдаёт его клиентскому
роутеру как **редирект**:

| запрос `/about-us` | Next 15.5.26 | Next 16.3.6 |
| --- | --- | --- |
| ответ | `200` + `x-middleware-rewrite: /en/about` | `307` + `location: /en/about?_rsc` |

Таргет rewrite — **внутренний** маршрут, поэтому роутер шёл на `/en/about`,
middleware канонизировал его обратно в `/about-us`, и так по кругу. Замер по
хопам:

```
/en/about-us → /about-us → /en/about?_rsc → /about-us → /en/about?_rsc → …
```

Дефект затрагивал **каждую** страницу с локализованным слагом и все три режима
префиксов. Проверка на Next 15 подтвердила, что это изменение поведения фреймворка,
а не ошибка в нашей логике: тот же middleware на 15 даёт `200`.

Решение: внутренний таргет распознаётся как **неподвижная точка** —
`canonicalPath(locale, canonical)` и `internalPath(locale, canonical)` сходятся.
Ограничение по `sec-fetch-dest`: заголовок `RSC` использовать нельзя, Next
вырезает его до вызова middleware (проверено — middleware с `RSC: 1` в изолированном
тесте отвечал `200`, а в живом приложении тот же запрос давал `307` с нашим
`x-next-locale`). Взята та же конвенция, что уже используется в `cookieValue`:
браузер шлёт `empty` для запросов роутера и `document` для навигаций, а
небраузерные клиенты не шлют ничего и сохраняют прежнее поведение. Поэтому
введенный вручную `/en/about` по-прежнему канонизируется и не становится
публичным дублем.

### Дефект 2: клиентское переключение локали не сохранялось

После устранения цикла цепочка всё равно приводила в `/ru/o-nas`. Причина —
тоже наша: ограничение `Set-Cookie` только документными запросами (внесено в этой
сессии ради кешируемости) подавляло куку и на **редиректах**, меняющих локаль.
Без куки следующий URL без префикса разрешался по старому значению.

Редиректы выведены из-под ограничения: сохранение выбора и есть смысл редиректа,
а `Set-Cookie` на `307` не делает целевую страницу некешируемой. Успешные
недокументные ответы куку по-прежнему не пишут — исходная цель сохранена.

Итог по всем четырём сценариям на Next 16.3.6:

| сценарий | результат |
| --- | --- |
| router fetch `/en/about-us`, кука `ru` | `307 → /about-us` (кука `en`) → `200` |
| router fetch `/ru/o-nas`, кука `en` | `200` |
| document `/en/about-us`, кука `ru` | `307 → /about-us` (кука `en`) → `200` |
| document `/ru/about` (внутренний путь) | `307 → /ru/o-nas` → `200` |

Оба дефекта закрыты четырьмя регрессионными тестами (V3-20, V3-20b, V3-21, V3-22):
неподвижная точка для запроса роутера, канонизация того же пути для документного
запроса, кука на редиректе при `sec-fetch-dest: empty`, и отсутствие куки на
успешном недокументном ответе.

**Побочные находки.** `npm run test:consumer` не был подключён к CI. Матрица не
могла доказать, какой именно Next она собирает: ячейки с 16 ставят `next@^16` в
корень и запускают `test:next`, поэтому сорвавшаяся установка молча тестировала бы
15 — добавлен шаг, печатающий разрешённую версию. README утверждал, что CI
запускает `test:next:16`; на деле CI гоняет `test:next` для всех ячеек, что
строже (против 16 выполняется весь набор, а не только интеграционный фикстур) —
формулировка исправлена.

## Одиннадцатый проход: `never` всё ещё зацикливался

После фикса интегральный фикстур покрывал только `as-needed`, хотя дефект
затронул все три режима. Тест, моделирующий поведение Next 16 (rewrite
превращается в редирект для запросов роутера), нашёл остаток:

```
never: /en/about-us → /about-us → (rewrite) /en/about → /about → /about-us → … CYCLE
```

Ветка `never` снимала префикс с внутреннего таргета, получая `/about`, — а это
тоже не канонический слаг (канонический `/about-us`), поэтому канонизация вела
обратно. Закрыто той же неподвижной точкой.

**Почему живой зонд этого не увидел.** `curl` не следует за
`x-middleware-rewrite`: он видит `200` и останавливается. Браузер через роутер
Next идёт дальше. То есть трассировка по хопам через curl в принципе не способна
обнаружить этот класс дефекта — нужна именно модель поведения фреймворка. Это
аргумент в пользу теста, а не ещё одного зонда.

**Негативный контроль.** Откат фикса в ветке `never` роняет `V3-23 (never)`;
возврат — снова 37/37. Значит, тест ловит ровно тот дефект, ради которого написан.

Итог по всем комбинациям (ходок до завершения, терминальный путь, кука):

| режим | запрос роутера | документная навигация |
| --- | --- | --- |
| `as-needed` | 3 хопка, `/en/about`, кука `en` | 2 хопка, `/about-us`, кука `en` |
| `always` | 2 хопка, `/en/about`, кука `ru` | 1 хоп, `/en/about-us`, кука `en` |
| `never` | 3 хопка, `/en/about`, кука `en` | 2 хопка, `/about-us`, кука `en` |

### Осознанный компромисс: `always` и кука при клиентской навигации

В `always` режиме `/en/about-us` уже каноничен, редиректа нет, а значит куку
ставить некуда. Единственный способ — писать `Set-Cookie` на успешный ответ, и
это сломало бы другое: **prefetch** ссылки на другую локаль менял бы локаль
посетителя. Проверено: `/ru/o-nas` при `sec-fetch-dest: empty` и куке `en`
отдаёт `200` без `Set-Cookie` (тест V3-25 фиксирует это как требуемое
поведение).

Цена компромисса мала и измерима: в `always` каждый URL несёт локаль, поэтому
кука нужна только на корне — `/` с кукой `ru` даёт `307 → /ru`. То есть после
чисто клиентского переключения закладка на корень вернёт старый язык, а полная
навигация — нет (на документном запросе кука ставится).

## Сравнение API с next-intl 4.14.7

Поверхность next-intl снята с его же деклараций типов (`dist/types/**`), а не из
документации, поэтому сравнение точное.

| next-intl | next-fluent | Вывод |
| --- | --- | --- |
| `server`: `getRequestConfig`, `getFormatter`, `getNow`, `getTimeZone`, `getTranslations`, `getMessages`, `getLocale`, `setRequestLocale` | все присутствуют | паритет |
| `server`: `getExtracted` | нет | **осознанно**: у next-fluent каталог — источник истины, `t('unknown')` и так ошибка типов; вместо этого поставляется `check --usage` |
| `navigation`: `Link`, `usePathname`, `useRouter`, `getPathname`, `redirect`, `permanentRedirect` | все присутствуют | паритет |
| `navigation`: `config` | **добавлено** | раньше не возвращался |
| `forcePrefix` на `Link`/`getPathname`/`redirect`/`useRouter` | **добавлено** | был единственный содержательный пробел |
| `redirect({href, locale, forcePrefix}, type)` | **добавлено** наряду с формой `(url, options)` | перенос вызовов не требует переписывания |
| `useRouter.bfcacheId`, `experimental_gesturePush` (Next 16) | проходят через `...router` структурно | паритет без явного кода |
| `localePrefix` как `Mode \| {mode, prefixes}` | есть | паритет |
| `localeCookie`, `localeDetection`, `alternateLinks`, `domains`, `pathnames`, `basePath` | есть | паритет |
| `./extractor` (extract, PO/JSON-кодеки) | нет | осознанно, см. выше |

Итого содержательный пробел был один — `forcePrefix`. Реализован во всех точках:
`Link`, `getPathname`, `redirect`, `permanentRedirect`, `useRouter.push/replace/prefetch`.

| режим | `getPathname('/about', 'en')` | с `forcePrefix` |
| --- | --- | --- |
| `always` | `/en/about` | `/en/about` (уже есть) |
| `as-needed` | `/about` | `/en/about` |
| `never` | `/about` | `/about` (no-op: префиксных URL там не существует) |

Проверено, что выданный URL каноничен для middleware во всех трёх режимах и что
разрешённая локаль совпадает с запрошенной (в `never` — через сигнальный URL
`switchLocaleHref`, как это делает `Link`).

Цена: ~28 B gzip собственного кода. Сначала реализация была сжата (экономия 2 B),
затем бюджет поднят `11.5 → 11.75 kB` с комментарием о причине — это стоимость
фичи, а не дрейф: защита по-прежнему срабатывает на росте свыше ~2%.

## Десятый проход: домены и round-trip typegen

Зона проверки — две последние крупные комбинации, которые матрица девятого
прохода не покрывала.

**A. `domains` × `pathnames` × `basePath`** (4 конфигурации). Инварианты: каждый
домен обслуживает свою локаль на своём каноническом слаге без редиректа;
`getPathname({locale, domain})` даёт URL, который на этом домене каноничен и
разрешается в нужную локаль максимум за один хоп; `basePath` не теряется ни в
`getPathname`, ни в hreflang; каждая hreflang-ссылка указывает на домен своей
локали и сама канонична. Все зелёные.

**B. Round-trip `typegen` → `t()`** на реалистичном каталоге: неймспейсы,
атрибуты, селекторы по числу и по роду, термы, комментарии, rich-теги,
литеральные фигурные скобки, пустое значение. Каждая объявленная в `.d.ts`
ключ-строка проверялась на разрешение через `t()` в обеих локалях. Все 21 ключ
разрешаются, ошибок форматирования нет; `t.attrs` возвращает оба атрибута;
`check --usage` не находит ложных `missing`.

**Дефектов не найдено.** Зафиксированное корректное поведение на границах:

| случай | поведение |
| --- | --- |
| `key =` без значения и атрибутов | Fluent считает это Junk: ключ не попадает в бандл, `check` сообщает `parse-error` и завершается с кодом 1 |
| сообщение только с атрибутами | `t.attrs` возвращает атрибуты; `t(key)` даёт `MISSING_MESSAGE` (значения действительно нет); `typegen` объявляет только `key.aria-label` |
| слаг чужой локали на чужом домене | остаётся на своём домене и канонизируется в слаг этой локали; междоменного редиректа нет — осознанный выбор, а не 404 |

Две мои ошибки в probe: регулярка вытаскивала из `.d.ts` не только элементы
union, но и имена аргументов (`amount`, `count`, `gender`), из-за чего шесть
проверок были ложными; и каталог в probe содержал невалидный `empty-value =`,
который инструмент справедливо отверг — это была ошибка каталога, а не кода.

## Девятый проход: сквозная матрица маршрутизации

Первый проход не по файлам, а по сценариям. Матрица `localePrefix` (always,
as-needed, never) × `pathnames` (нет, слаги) × маршрут × локаль — 6 конфигураций,
проверяемых на сквозные инварианты, которые юнит-тест по одному модулю выразить
не может:

1. URL, который выдаёт `Link`, достигает канонической страницы максимум за один
   хоп (сигнальный URL в `never` обязан редиректить ровно один раз);
2. rewrite заканчивается на ожидаемом внутреннем маршруте;
3. разрешённая локаль совпадает с запрошенной;
4. циклов редиректов нет ни на одном варианте;
5. каждая hreflang-ссылка сама канонична.

Найден **один реальный дефект**: middleware определял локаль только по префиксу,
куке и `Accept-Language` — но не по URL. При `pathnames` слаг принадлежит ровно
одной локали, поэтому в режиме `never` (префиксов нет) первый визит на `/o-nas`
без куки разрешался в дефолтную локаль и редиректил на `/about-us` — общая
ссылка на русскую страницу приводила на английскую.

Правило после двух итераций: локаль выводится по слагу, который принадлежит
ровно одной **недефолтной** локали.

| запрос | было | стало |
| --- | --- | --- |
| `/o-nas`, `never`, без куки | 307 → `/about-us`, локаль `en` | 200, локаль `ru` |
| `/o-nas`, `as-needed`, без куки | 307 → `/about-us`, `en` | 307 → `/ru/o-nas`, `ru` |
| `/o-nas` + кука `en` | 307 → `/about-us`, `en` | без изменений (кука — явный выбор) |
| `/about-us` + `Accept-Language: ru` | 307 → `/ru/about-us` | без изменений |

Первая версия правила («слаг ровно одной локали») сломала тест V3-04: слаг
дефолтной локали — это общая форма, на которую попадает обычный визит, и он не
должен перебивать `Accept-Language`. Сужение до недефолтных локалей удовлетворяет
обоим случаям; оба закреплены тестами (V3-19, V3-19b, V3-19c).

Три моих ошибки в probe, из-за которых он сначала давал ложные FAIL: проверка
внутреннего маршрута для корня (в app router это `/{locale}`, а не `/`);
`getPathname` вместо пути `Link` — в `never` канонический href намеренно не несёт
локаль, её добавляет `switchLocaleHref` сигнальным URL; и stateless-куки между
хопами — браузер переносит `Set-Cookie` через редирект, а мой jar нет, из-за
чего сигнальный URL выглядел теряющим локаль. После исправления probe матрица
зелёная целиком.

## Седьмой проход: server.ts и client.ts

Зона проверки — request-scoped состояние (`server.ts`, 492 строки) и клиентский
провайдер (`client.ts`, 353). 15 проверок. **Воспроизводимых дефектов не найдено** —
это первый проход без них, и он подтверждает, что предыдущие закрыли реальное,
а не исчерпали список.

Опровергнутые гипотезы (проверены замером, а не рассуждением):

| Гипотеза | Результат |
| --- | --- |
| React `cache()` мемоизирует глобально вне request scope → состояние утекает между запросами | Опровергнуто: в React 19.3.0 два вызова `getRequestStore()` вне scope дают разные объекты, `isRequestScopeActive()` корректно возвращает `false` |
| Слот кэша бандла не учитывает `functions` → чужие функции в закэшированном бандле | Опровергнуто: `hasCustomFuncs` полностью обходит кэш при наличии функций или `requestConfig` |
| Подмена сообщений между локалями при нормализующем конфиге | Воспроизвести не удалось вне request scope: при `requestConfig` кэш обходится, а без него store создаётся заново на каждый вызов |
| `getFormatter` берёт `timeZone` первого загруженного конфига | Опровергнуто: `config.timeZone` имеет приоритет над `store.timeZone` |
| `computeSourceHash` даёт коллизии → клиент рендерит чужие сообщения | Опровергнуто: в `createFluentBundle` хэш сверяется с исходником через `sameSource`, форма ключа для строки и для массива различима |

Одно улучшение по результату чтения (не воспроизведено): ключ слота бандла
строился по `effectiveLocale`, тогда как сообщения грузятся для **запрошенной**
локали. Конфиг, нормализующий несколько запрошенных локалей в одну
(`en-GB` и `en` → `en`), в пределах одного запроса мог отдать первому
сообщения второго. Ключ теперь содержит обе локали. Теста нет: случай требует
живого React request scope, которого юнит-харнесс не даёт; изменение только
сужает ключ кэша и регрессий не вносит.

Проверено и признано корректным: `setRequestLocale` вне request scope бросает в
разработке и предупреждает в production; неподдерживаемая и некорректная локаль
отклоняются с значением в сообщении; конфиг с мусором вместо messages и с
битной локалью даёт внятные ошибки; бросающий `onError` не ломает рендер;
провайдер рендерит FTL, JSON-каталог и готовый бандл; смена сообщений и локали
между рендерами меняет вывод; `useIsolating` соблюдается на клиенте;
отсутствующий ключ рендерит фолбэк, а не падает.

Одна моя ошибка в probe: `$n` — аргумент сообщения и передаётся через `t(key, args)`,
а `defaultTranslationValues` несёт значения для rich-текста; первая версия
проверки падала с `Unknown variable: $n` и меряла не то.

| 1 | **Обход проверки опасного href** | `assertSafeHref('java\tscript:alert(1)')` не бросал; то же для `\n`, `\r`, `dat\ta:`, `vbscript\t:` и ведущих C0-символов — 7 вариантов. Браузеры вырезают tab/LF/CR из URL до разбора схемы, поэтому такой href исполняется | guard проверяет URL таким, каким его увидит браузер; отклонённое значение экранируется в сообщении, чтобы не переписать собственную строку лога |
| 2 | **Ошибка каталога без имени файла** | битый `en.json` → `Unexpected end of JSON input`, непонятно какой из локалей | `[next-fluent] Cannot read the catalog <путь>: <причина>`; покрывает и ошибки `jsonToFluent` |
| 3 | **Symlink-каталог молча терялся** | `readdirSync(withFileTypes)` не считает symlink ни файлом, ни каталогом → связанный `en.ftl` пропускался, сообщения просто пропадали | классификация через `stat`, и только как файл — каталожный symlink не создаёт цикл рекурсии |

Граница риска по дефекту 1 установлена точно: `Link`/`getPathname` сами по себе
не эксплуатировались, потому что нераспознанная схема превращалась в
относительный путь (`/en/java\tscript:alert(1)`), — но `assertSafeHref`
экспортируется как средство проверки недоверенных href, и именно этот контракт
нарушался. Теперь такой href отклоняется outright.

Проверено и признано корректным: обычные href (`/about`, `mailto:`, `#frag`,
внешние) не затрагивы; `__proto__.ftl` остаётся обычным ключом локали; пустой
каталог не бросает; pseudo-локализация сохраняет placeables, теги и вложенные
селекторы. Одно моё ожидание оказалось неверным: `Save` → `[Šåṽé]`, а не
`[Šåvé]`, потому что `CHAR_MAP` отображает `v` в `ṽ`.

## Пятый проход: rich-текст, форматтер, кэш, alternate-links

Зона проверки — четыре модуля, которые не зондировались ни разу: `rich.ts`,
`formatter.ts`, `lru.ts`, `alternate-links.ts`. 17 проверок, найдено **три
реальных дефекта**, все закрыты тестами.

| # | Дефект | Воспроизведение | Исправление |
| --- | --- | --- | --- |
| 1 | **Невидимые bidi-метки в HTML-атрибутах** | `t.plain('hello', {name:'John'})` → `"Hello ⁨John⁩"` (U+2068/U+2069) для `aria-label`/`title`/`alt`/`<meta>` | `stripRichText` снимает метки на всех путях, а не только при наличии разметки — ранний выход обходил собственное документированное поведение |
| 2 | **Спам в логах** | неизвестное имя формата (`'nope'`) логировалось на каждый вызов: 1000 строк списка → 1000 предупреждений, хотя комментарий обещал «reported once» | одно предупреждение на имя формата за процесс, множество ограничено 200 записями |
| 3 | **Запись со значением `undefined` не обновляла recency** | `get()` проверял значение, а не наличие ключа, поэтому такая запись рано вытеснялась | проверка через `map.has`; сейчас ни один вызывающий код `undefined` не хранит, дефект был латентным |

Проверено и признано корректным: вложенные одноимённые теги; кэш форматтера
учитывает локаль и `timeZone`; опции со значением `undefined` не collides в
ключе кэша; размер LRU ограничен при 1000 записей; `search` и `basePath`
попадают во все варианты alternate-ссылок; локаль на отдельном домене не
дублируется на основном origin.

Пять моих же ожиданий в probe оказались неверны: тег с атрибутами
(`<a href="…">`) — документированное ограничение (теги без атрибутов), а
некорректная разметка остаётся экранированным текстом, что безопасно;
незакрытый тег — тот же безопасный фолбэк; `Map`-подобный API в принципе не
отличает «хранится `undefined`» от «ключа нет», поэтому значимое свойство —
обновление recency, а не различение промаха; `origin` по контракту origin
(путь относится к `basePath`, что проверено отдельно); `x-default`, ведущий на
URL дефолтной локали, — корректная практика hreflang, а не дубль.

## Четвёртый проход: маршрутизация, round-trip каталога, форматирование

Третий проход проверял только новый код (`usage.ts`, CLI). Этот расширил зону
проверки на области, которые раньше adversarial-не зондировались: матрица
маршрутизации middleware, round-trip каталога, форматирование, кэш бандлов.
16 проверок, найдено **два реальных дефекта**, оба закрыты тестами.

| # | Дефект | Воспроизведение | Исправление |
| --- | --- | --- | --- |
| 1 | **Дубли контента при `pathnames`** | `/ru/about` и `/ru/o-nas` отдавали одну страницу без редиректа; `/en/o-nas` отдавал русский слаг под английской локалью | middleware приводит путь к каноническому для разрешённой локали (307) во всех трёх режимах `localePrefix`, пропуская собственный rewrite-проход, чтобы не зациклиться |
| 2 | **Ложный `missing` при двух биндингах** | два компонента в одном файле: `const t = useTranslations('checkout')` и `const t = useTranslations('nav')` — первый вызов резолвился против второго неймспейса | биндинги хранятся в порядке исходника, резолвятся по ближайшему предыдущему; неоднозначный случай уходит в `dynamic` |

Проверено и признано корректным: открытые редиректы закрыты (`/ru//evil.example/x`
и варианты с `\`, `///`, `%2f` остаются same-origin); query и фрагмент
сохраняются при редиректе; `basePath` не теряется; входящий заголовок
`x-next-fluent-rewrite` не подделывается; скалярные JSON-значения (`42`, `true`,
`0`, `""`) форматируются корректно; `t.plain` вырезает разметку; один и тот же
источник под разными локалями даёт разные бандлы.

Четыре моих же ожидания в probe оказались неверны, дефектами они не являются:
уже канонический путь корректно отдаёт 200; round-trip JSON→FTL не
байт-в-байт из-за bidi-меток `useIsolating: true` (документированный дефолт —
при `useIsolating: false` round-trip точен, что проверено отдельно); значения
`t.attrs` могут содержать `"`/`<`/`>`, потому что атрибуты экранирует React;
`createFluentBundle('en-0', …)` бросает исключение по замыслу — тег локали
валидируется.
