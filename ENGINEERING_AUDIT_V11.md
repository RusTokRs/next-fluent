## 1. V11-01 (P1). Симлинк в дереве исходников делал сообщение мёртвым

**Воспроизведение.**

```
app/page.tsx              → t('in-page')
app/components → ../../packages/ui   (симлинк на каталог)
packages/ui/Button.tsx    → t('from-shared')
```

```
$ next-fluent check --input messages --src app --usage
Usage against en: 1/2 keys used, 0 dynamic call site(s).
unused (1)
  "from-shared" is defined in en but never referenced in the scanned sources.
```

С `--strict-usage` то же самое становится **провалом сборки в CI**.

**Причина.** `fs.Dirent` для симлинка не является ни `isFile()`, ни
`isDirectory()`, поэтому запись отсеивалась обеими проверками подряд и
исчезала. Соседний по файлу `collectCatalogFiles` ровно это уже чинил — в V5, с
комментарием «linked catalogs were silently dropped» — но сознательно ограничил
свою правку каталогами, чтобы ссылка на каталог не завела цикл. Обход исходников
остался с поведением по умолчанию, то есть с **противоположным** и не
задокументированным.

**Исправление.** Ссылки разворачиваются через `fs.statSync`, как в
`collectCatalogFiles`. Цикл (`app/components → .. → app`) становится возможен, и
поэтому запоминается реальный путь каждого посещённого каталога и каждого
собранного файла: повтор пропускается, а не обходится и не считается дважды.

Побочный эффект дедупликации — тот же, что нужен: один файл за двумя ссылками
это один файл, иначе его места вызова были бы посчитаны дважды.

| | было | стало |
| --- | --- | --- |
| ссылка на файл | не найден | найден |
| ссылка на каталог | не найден | найден |
| ссылка на собственного предка | — | обход завершается |
| два каталога за ссылками | — | сканируется один раз |
| один файл за двумя ссылками | — | собирается один раз |
| битая ссылка | — | пропускается, без исключения |
| `node_modules` за ссылкой | — | по-прежнему пропускается |

## 2. V11-02 (P2). `.mts`, `.cts` и `.mdx` не считались исходниками

**Воспроизведение.**

```
app/page.tsx    → t('in-tsx')
app/server.mts  → t('in-mts')
app/page.mdx    → t('in-mdx')
```

```
Usage against en: 1/3 keys used, 0 dynamic call site(s).
unused (2)
  "used-in-mdx" is defined in en but never referenced in the scanned sources.
  "used-in-mts" is defined in en but never referenced in the scanned sources.
```

**Почему это не выдумка.** `.mts`/`.cts` — стандартные расширения TypeScript для
ESM/CJS-модулей (TS 4.7+); монорепозиторий с `"type": "module"` получает их
естественным путём. `.mdx` — официальный плагин Next, и страница на нём
вызывает хуки как любая другая. Список расширений писался, когда последними
добавками были `.mjs`/`.cjs`, и с тех пор не пересматривался.

**Исправление.** В список добавлены `.mts`, `.cts`, `.mdx`. Заодно проверка
`.d.ts` обобщена до `/\.d\.[cm]?ts$/`: иначе `.d.mts` попадал бы в разбор как
исходник. Проверено, что объявление в `.d.mts` не может выдать мёртвое сообщение
за живое.

**Что нарочно не добавлено:** `.vue`, `.svelte`, `.markdown`, `.json`,
`.mtsx`. Первые — не Next, `.json` не содержит мест вызова, `.mtsx` не является
расширением TypeScript. Список расширений не должен становиться «на всякий
случай».

**Проверено отдельно:** анализатор мест вызова — не парсер, а маскировщик
строк, комментариев и регулярных выражений. На реальном `.mdx` с прозой,
обратными кавычками, кавычками и регулярным выражением он отрабатывает верно:
`t("in-mdx")` внутри текста в кавычках не считается вызовом, а настоящий вызов
считается.

## 3. V11-03 (P3). Пути отказа наблюдателя не проверены

`watchCatalogs` — единственная подсистема файлового ввода-вывода, которая
работает, **пока человек правит файл**. Ошибки там приходятся на полусохранённый
файл, а не на готовый.

Проверено пробником: наблюдатель в режиме `fs.watch` на битом каталоге отдаёт
ошибку в `onError`, после исправления файла отдаёт `onUpdate`, а объявления
перезаписываются. Поведение верное — правки кода не потребовалось, но до этого
момента оно не было проверено ничем. Закрыто тестом: ошибка → `onError`,
исправление → `onUpdate` с перезаписью файла объявлений. Заодно закреплён
пропуск `node_modules`, `.next`, `dist`, `.git`, `coverage` — теперь это часть
гарантии «ссылки обходятся», а не деталь реализации.

## 4. Ошибка в приоритетах прошлого прохода

§9 отчёта V10 предлагал начать с «непокрытых веток `watchCatalogs`». Их нет:
`watchCatalogs` покрыт с V5 в `test/hardening.test.mjs` и
`test/audit-v5-coverage.test.mjs`, обе модели — и `fs.watch`, и опрос по таймеру.
Непокрыты были `catch` вокруг `readdirSync`, `catch` вокруг `catalogSnapshot`,
`catch` вокруг `statSync` и `catch` вокруг `fs.watch` — то есть защитные ветки на
недостижимых в обычной жизни событиях (нет прав, гонка, исчерпание inotify).

Исправлен сам список приоритетов, а не код: эти четыре `catch` оставлены как
есть, потому что удалять защиту ради процента покрытия — не инженерия.

## 5. Что проверено и оказалось в порядке

- **`watchCatalogs`, обе модели.** `fs.watch` и опрос по `unref`-таймеру
  переживают битый каталог и восстанавливаются после исправления.
- **Пропускаемые каталоги** по-прежнему пропускаются, в том числе `node_modules`
  **за симлинком** — обход ссылок не отключает список.
- **`.mdx` и маскировщик мест вызова.** Проза, обратные кавычки, регулярные
  выражения и настоящие вызовы различаются верно.
- **Покрытие `client.js` (70.2 % ветвей) и `navigation.js` (59.5 %)** — оставлено
  как есть, и это решение, а не недосмотр: непокрытые ветки — `back()`,
  `forward()`, `refresh()` и обёртка `NextLink`, то есть делегаты, работающие
  только внутри контекста App Router. В Node их нечем накрыть, а браузерные
  прогоны CI недоступны локально. Дописывать тест, который нельзя выполнить,
  было бы нарушением метода.

### Тест, который прошёл только в CI

Первая отправка прохода упала **на всех четырёх Windows-задачах**, при этом
локально всё было зелёным, а логи задачи недоступны из этой среды: GitHub
отдаёт их с `productionresultssa12.blob.core.windows.net`, которого нет в списке
разрешённых хостов. Единственный репортер — матрица CI, и понадобилось два
предположения, чтобы дойти до причины:

1. **Windows не даёт создавать симлинки** без Developer Mode — правда, но это
   было лишь первое из двух. Защита добавлена по соглашению репозитория.
2. **`path.relative` возвращает разделитель платформы**, а все ожидания в новом
   файле записаны через `/`. На Linux обе формы совпадают, поэтому ошибка
   невидима локально и видна только на Windows. Это и была причина падения.
   Исправлено именованным помощником, у которого есть собственный тест —
   иначе гарантия снова осталась бы непроверяемой на машине, где разделитель
   уже `/`.
3. Попутно убран ещё один источник случайных сбоев: тест наблюдателя спал
   400 мс и ждал ровно одно событие. Windows-раннер отдаёт событие позже, а
   `fs.watch` может сообщить одну запись несколькими событиями. Теперь ждёт
   нужное состояние до дедлайна — как уже сделано в существующем тесте
   наблюдателя.

Вывод, который стоит сохранить: **тест, написанный на Linux, проверяется на
Linux**. Матрица — не формальность, а единственный инструмент, которым
проверяется код, который сюда не доехал.

## 7. Приоритеты следующего прохода

1. **`client.js`, 70.2 % ветвей.** Разбирать только те ветви, что достижимы
   через `renderToStaticMarkup` (например, `fallbackBundles` строкой/массивом);
   остальное — контракт с браузером.
2. **`LocalizedLink` (0 тестов).** Обёртка рендерится Next'овым `Link` и вне
   App Router не поднимается. Раз уж CI всё равно гоняет браузерные прогоны,
   проверку стоит добавить **туда**, где она выполнима, а не писать тест в Node,
   который нельзя прогнать.
3. **`usage.js`, 88.0 % ветвей.** Непокрыты ветви разбора мест вызова — самый
   густой участок кода во всей библиотеке и самый склонный к тихим ошибкам.
4. **`catalog-io.js`, четыре защитных `catch`.** Закрывать только если найдётся
   реальный сценарий, где защита даёт неверный результат.
