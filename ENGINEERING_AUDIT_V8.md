## 1. V8-01 (P1). Символы, которые браузер выбрасывает из URL, прятали чужой origin

**Воспроизведение.** Браузер перед разбором URL удаляет из него ASCII tab, LF и
CR в любом месте строки. Значит `href: "/\n/evil.example"` — это не путь с
переводом строки, а протокол-относительный `//evil.example`, то есть **другой
хост**. Пробник (6 конфигураций × 4 режима) до правки:

```
as-needed  "/\n/evil.example"            -> "/\n/evil.example"   → https://evil.example
never      "/\t//evil.example"           -> "/\t//evil.example"  → https://evil.example
always     "/\r/evil.example"            -> "/\r/evil.example"   → https://evil.example
```

Причина: `resolveLocalizedPathname` решал вопрос «внутренний это путь или
внешний» по сырой строке (`isExternalUrl(href)`), а ведущую серию разделителей
схлопывал `normalizeLeadingSlashes` — уже после этого решения и без учёта того,
что серия может быть «разорвана» невидимым для парсера символом. В режимах
`always`/`as-needed` для не-дефолтной локали спасал добавляемый префикс, поэтому
дыра была видна только в части режимов — как и у V6-01.

**Правка.** Нормализация читает строку так, как её прочитает парсер:

- `stripUrlDiscardedControls` (внутри `normalizeLeadingSlashes`) удаляет
  tab/LF/CR *до* проверки ведущей серии — точка одна, через неё проходят все
  вызовы (`resolveLocalizedPathname`, `middleware`, `locale-prefix`);
- в `resolveLocalizedPathname` схлопывание перенесено **до** снятия `basePath`,
  поэтому испорченный `"/\n/app/docs"` теперь даёт тот же href, что и чистый
  `"/app/docs"` (до правки получалось `"/app/ru/app/docs"`);
- `switchLocaleHref` (внутренняя, из подпутей пакета не экспортируется) тоже
  считает от нормализованной цели. Это защита от будущего вызова: сегодня оба
  её вызывающих передают результат `resolveLocalizedPathname`, и через публичный
  API дыра в ней недостижима — так и написано в отчёте, а не выдано за находку.

**Проверка.** Тот же пробник: 138 разобранных href (6 конфигураций, включая
`basePath`, кастомные префиксы и per-domain режимы) — **0 уходов с origin**.
Единственное, что осталось «уходить», — `//cdn.example/x`: это документированный
passthrough внешних ссылок, он закреплён тестом `V8-01: an external href stays
external, by design`, чтобы следующая правка не «починила» его.

## 2. V8-02 (P1). `<FormattedMessage>` не сканировался вообще

**Воспроизведение.** `<FormattedMessage id="k-one" />` — документированный
способ отрендерить сообщение из компонента, и его `id` — такой же литеральный
ключ, как аргумент `t()`. Анализатор смотрел только на вызовы, поэтому:

```
<FormattedMessage id="k-one" />          -> usedKeys: []      issues: unused:k-one
```

То есть ключ, который рендерится, попадал в отчёт как мёртвый — а это тот самый
ложный `unused`, ради отсутствия которого анализатор и написан
(`--strict-usage` на таком проекте падает). Не помогали ни порядок атрибутов,
ни перенос строки, ни `id={'k-one'}`.

**Правка.** Добавлен разбор JSX: имена атрибутов читаются по маскированной копии
(там строковые литералы пусты, поэтому `data-id="…"` не может выдать себя за
`id`), значение — по исходному тексту. Литерал в кавычках, в выражении и в
шаблоне без подстановок даёт ключ; нелитеральный `id` или только `{...props}`
не молчат, а попадают в `dynamic` с источником `<FormattedMessage>`. Ключи
компонента ищутся по **всем** пространствам имён (компонент берёт транслятор из
контекста, а не из namespace-аргумента), поэтому вердикта `missing` у этого
источника не бывает — только `dynamic`, и в тексте предупреждения это сказано:
«matches no catalog key (every namespace was searched), so it cannot be verified».

## 3. V8-03 (P2). Комментарий внутри первого аргумента делал ключ нечитаемым

**Воспроизведение.**

```
const t = useTranslations();
t('home-title' /* keep */, { n: 1 });   -> dynamic (ложный), ключ не зачтён
t(/* pick */ 'home-title');             -> dynamic (ложный)
```

`readFirstArgument` читал исходник как есть и на `'key' /* … */` не срабатывал
`staticString`; при отсутствии binding такой вызов вообще молча пропускался.

**Правка.** `readFirstArgument` заменён на `readArgumentList`: он возвращает
список аргументов, удаляя комментарии (строчные и блочные) и отслеживая кавычки,
скобки и шаблонные литералы — поэтому запятая внутри строки или объекта не
разрезает аргумент, а комментарий не попадает в текст ключа. Чтение *всех*
аргументов понадобилось ещё и V8-04.

## 4. V8-04 (P1). `createTranslator` читал пространство имён не там, где оно лежит

**Воспроизведение.** У этой фабрики первый аргумент — bundle, а пространство
имён идёт вторым (строкой, полем `namespace` в options или третьим аргументом,
если вторым передан fallback-bundle):

```
createTranslator(bundle, 'checkout')                 -> t('total') → missing:total
createTranslator(bundle, { namespace: 'checkout' })  -> t('total') → missing:total
createTranslator(bundle, null, 'checkout')           -> t('total') → missing:total
```

`namespaceOf` читал только первый аргумент и видел там `bundle`, поэтому binding
считался *глобальным*, а верно названный ключ — отсутствующим: команда падала.

**Правка.** Введена таблица `NAMESPACE_ARGUMENT` (`useTranslations`/`getTranslations`
— с нулевого аргумента, `createTranslator` — с первого) и трёхзначный разбор
`factoryNamespace`:

- литерал (строка или `namespace:` в объекте) — ключи проверяются по нему;
- ничего, что может нести namespace (`createTranslator(bundle)`,
  `createTranslator(bundle, null)`, объект options без `namespace`) —
  это **глобальный** транслятор, и неизвестный ключ у него по-прежнему
  `missing`, что верно;
- аргумент есть, но не читается (`{ ...opts }`, `nsVar`) — ключи сверяются со
  всеми пространствами, и несовпадение даёт `dynamic`, а не `missing`.

## 5. V8-05 (P1). Нечитаемое пространство имён превращало «не знаю» в «нет такого ключа»

**Воспроизведение.** `useTranslations(NS)` / `getTranslations(NS.checkout)`:
namespace есть, но не литерал. До правки binding считался известным, ключ
искался в глобальном пространстве — и `missing:total` падал на живом коде.

**Правка.** Это третье состояние из V8-04: `namespaceKnown: false` +
`namespaceNote` («создан с аргументом, который не является строковым
литералом»). Разрешение идёт по всем пространствам, и здесь важны обе стороны:

- ключ, который где-то совпал (`t('title')` при `home-title` в каталоге),
  **зачитывается** — иначе получился бы ложный `unused` (закреплено тестом);
- ключ, который не совпал нигде, — `dynamic` с объяснением, а не `missing`.

## 6. V8-06 (P2). Что считается строковым литералом

**Воспроизведение.** Разбор был жадным по кавычкам:

```
t('k-' + 'one')        -> missing: "k-' + 'one"   ← ключ, которого не может быть в каталоге
                       -> unused: k-one, k-two    ← и оба настоящих ключа объявлены мёртвыми
t('k-one' as const)    -> dynamic (ложный)
t('k-one' satisfies Key) -> dynamic (ложный)
```

**Правка.** `staticString` теперь читает литерал как литерал: находит его
кавычку и конец (с учётом экранирования, с запретом подстановок в шаблоне) и
требует, чтобы после литерала оставалась только «типовая» синтаксическая
надстройка, которую компилятор стирает (`as …`, `satisfies …`, `!`). Значение
при этом не меняется никакой ассерцией, поэтому `t('key' as const)` — тот же
ключ, что `t('key')`; а выражение — это выражение, оно попадает в `dynamic`.
Плюс, естественно, `t('k-one + k-two')` остаётся литералом `k-one + k-two`:
плюс внутри кавычек оператором не является (закреплено тестом).

## 7. V8-07 (P3). Опциональные вызовы были невидимы

`t?.('key')`, `t?.rich('key')`, `t.rich?.('key')` — ни один не находился, и ключ,
использованный только так, попадал в `unused`. Это не экзотика: `?.` появляется
при рефакторинге кода, где транслятор мог быть необязательным. Правка — одна
группа в регулярном выражении вызовов (`(?:?.|.)?` перед именем метода), плюс
тест на все четыре написания.

## 8. V8-08 (P2). Валидная таймзона объявлялась неизвестной, потому что Intl не понравились опции

**Воспроизведение.**

```
createFormatter({ locale: 'en-GB', timeZone: 'UTC' })
  .dateTime(date, { dateStyle: 'short', timeZoneName: 'short' })
-> console.warn: Unknown time zone "UTC" (see `requestConfig.timeZone`)
-> "2026-01-02T03:04:05.000Z"
```

`Intl.DateTimeFormat` бросает на всю конфигурацию целиком: и на неизвестную
зону, и на запрещённое сочетание (`dateStyle`/`timeStyle` вместе с любым
компонентным полем — это TypeError, у которого в V8 текст «Invalid option :
option», то есть вообще без подсказки). Обработчик ошибки считал виноватой зону
всегда — и отправлял читателя править конфиг, где всё было верно, а в UI
попадала ISO-строка.

**Правка.** На пути ошибки (только там) зона проверяется отдельно: `usableTimeZone`.
Дальше две честные ветки:

- зона плоха — как раньше: одно предупреждение «Unknown time zone», повтор без
  зоны, текст остаётся локализованным;
- зона в порядке — значит, отказали опции. Если среди них есть `dateStyle`/
  `timeStyle` и повтор без них удаётся, стиль отбрасывается (значение остаётся
  локализованным, `"02/01/2026, UTC"`), и предупреждение называет правило, а не
  зону. Если спасти нечем (`hourCycle: 'x'`, `fractionalSecondDigits: 9`) —
  сообщается именно «Intl refused these dateTime options … the value was rendered
  as an ISO string», без выдуманного объяснения.

Тест `V8-08` намеренно фиксирует все три исхода, включая тот, где объяснения нет:
предупреждение, называющее не ту причину, — это тот же класс дефекта, что и
ложный `missing`.

## 9. Что проверено и оказалось в порядке

Проверялось пробниками против `dist/`, чтобы следующий проход не повторял:

- `src/rich.ts` — неизвестные теги остаются экранированным текстом, вложенность,
  самозакрывающиеся и void-теги, незакрытые теги восстанавливаются как текст,
  атрибуты внутри тега не разбираются (значение с `class="x"` — просто текст);

- `src/pseudo.ts` (pseudo-localization) — результат повторно парсится Fluent
  без единой Junk-записи, id/плейсхолдеры/селекторы/ссылки на термы сохранены,
  `pseudoLocalizeText` не трогает плейсхолдеры и не-ASCII;
- `src/catalog.ts` (JSON → FTL) — 45 «неудобных» значений (кавычки, обратные
  слэши, `{}`, `#`, `*`, `[`, `=`, переводы строк и CR, tab, эмодзи, пробелы по
  краям, пустая строка, `\u0000`) проходят конвертацию **байт-в-байт** через
  парсер Fluent; вложенность, `""`-значение, пунктирные и дефисные ключи,
  дубли id и глубину проверяют уже существующие тесты; экранирование `\{`/`\}`
  и `{count}` → `{ $count }` — документированные правила, а не дефекты;
- `src/pick-messages.ts` — прунинг по namespace сохраняет атрибуты, транзитивные
  ссылки на термы и сообщения, порядок записей; junk внутри своего namespace —
  ошибка, junk чужого — нет; префиксные совпадения `checkout` / `checkout-total`
  обрабатываются одним правилом;
- `src/route-engine.ts` — приоритет маршрутов (терминатор > статический сегмент >
  одиночный параметр > catch-all > опциональный catch-all) разобран на всех
  пересекающихся парах, включая `[id]` против `[[...slug]]` и `[id]` против
  `[...rest]`; декодирование сегментов и `encodeURIComponent` при рендере
  защищают от подстановки слэша;
- `src/alternate-links.ts` — прочитан целиком, находок нет;
- `src/formatter.ts`, путь чисел и `relativeTime` — `NaN`, `Infinity`, `-0`,
  большие числа, список, несовместимые опции: значения не портятся; `unit:
  'nope'` молча даёт число без единицы — это осознанно оставлено (неверный
  результат не выдаётся за верный, а диагностику ради диагностики не добавляли).

### Решение по клиентскому бюджету

Проход потратил 695 B min (из них 155 B — V8-01, ≈540 B — V8-08) и упёрся в
прежний бюджет вплотную (48.0 при 47.5 kB). Развилка была ровно та, что описана
в V7 §7: не поднимать, а сузить публичную поверхность браузерного энтри
(`resolveAcceptLanguage`, `checkCatalogs`, pseudo-localizer) — или признать рост
по факту. Замер решил вопрос:

```
бандл фикстуры потребителя:  resolveAcceptLanguage — отсутствует,
                             checkCatalogs — отсутствует,
                             pseudo-localizer — отсутствует
                             jsonToFluent — присутствует (его использует
                             FluentProvider для JSON-каталогов)
```

То есть приложение, которое этих функций не вызывает, за них уже ничего не
платит — их вырезает tree-shaking. Сужение энтри ничего никому не сэкономило бы,
а вызывающим сломало бы импорт; поэтому бюджет поднят на измеренную величину
(+0.5 kB min, +0.25 kB gzip по фикстуре, +1.0 kB по собственному коду), и это
единственное повышение прохода. Запас после пересчёта — 0.54 kB min / 0.29 kB
gzip от реально скачиваемого объёма; в предыдущем проходе он был 0.4 / 0.35 kB,
то есть бюджет стал не свободнее, а честнее: он растёт только вместе с кодом,
который браузер действительно получает.

## 11. Приоритеты следующего прохода

1. **Первый живой `workflow_dispatch publish.yml` — после мержа PR #7.**
   `workflow_dispatch` существует только для файлов из ветки по умолчанию, а
   `publish.yml` появился здесь, поэтому до мержа GitHub отдаёт 404 (проверено
   ещё в V7). Локальный эквивалент — полный `npm publish --dry-run` — прогнан.
2. **Браузерные прогоны (`test:next:browser`, `test:next:domains`) в песочнице
   недоступны** (Chromium не скачивается) и подтверждаются только CI PR #7.
3. **Клиентский бюджет: следующий шаг — снова замер, а не рефлекс.** Запас
   0.54 kB min; если очередная правка клиентского графа его исчерпает, первым
   вопросом должен быть не «поднять ли бюджет», а «сколько это стоит браузеру и
   нельзя ли получить то же дешевле» — ровно как с V8-08, где решение о цене
   принималось по замеру, а не заранее.
4. **`--usage`: следующий кандидат — формат отчёта, а не разбор вызовов.**
   Разбор покрыт тестами на все документированные формы; если искать дальше, то
   не «ещё один вид вызова», а качество вывода (например, группировка `dynamic`
   по файлам при больших кодовых базах).
