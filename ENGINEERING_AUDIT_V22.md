## 3. V22-01. Публичный класс с методом, который никто не звал

Выбор цели в этом проходе не по вкусу, а по данным: `npm run coverage` (гейт из
V21) печатает таблицу по `dist/`, и самые слабые строки в ней выглядели так:

```
 84.73  85.50  95.24   server.js       (потолок, разобран в V19)
 94.66  87.84  88.46   client.js       (ограничение по V15 §4)
 95.00  86.21  91.30   catalog-io.js
 95.56  97.92 100.00   catalog.js
 95.56 100.00  87.50   lru.js          ← строки 34–35
```

Непокрытыми в `lru.js` оказались строки 34–35 — метод `delete()`. Здесь важна
проверка, которую легко пропустить: `LRUCache` **экспортируется из публичного
API** (`src/index.ts:74`, реэкспорт в `dist/bundle.d.ts`), то есть это не
внутренний вспомогательный класс, а часть контракта пакета. И внутри библиотеки
`delete()` не вызывает никто — `grep` по `src/` не даёт ни одного обращения.

То есть публичный метод существовал, ничем не проверялся и ничем не
использовался. Ветка вытеснения при этом была покрыта — первое чтение непокрытых
строк как «ветка вытеснения» было неверным, номера указывали на `delete`.

Закрыто шестью тестами на весь публичный контракт класса, а не только на
`delete`: удаление и его возвращаемое значение, освобождение места (без
удаления следующая вставка вытеснила бы LRU), порядок вытеснения и обновление
MRU через `get()`, перезапись существующего ключа без вытеснения, хранимый
`undefined` как попадание (а не промах), `clear()` и отклонение некорректного
размера (`0`, `-1`, `1.5`, `NaN`, `Infinity`).

```
dist/lru.js   100.00 строки / 100.00 ветки / 100.00 функции
```

## 4. V22-02. Заголовок hreflang против остальной библиотеки

`buildAlternateLinksHeader` собирает URL для каждой локали самостоятельно:
`externalTemplate` → `renderTemplate` → префикс → basePath. Навигационный код
строит те же URL другим путём — через `localizePath` и правила
`locale-prefix.ts`. Если два пути разойдутся, поисковик пошлёт пользователя по
адресу, который приложение редиректит в другое место.

Прогон: 10 конфигураций — три режима префикса, basePath, динамический маршрут
`/news/[slug]`, три локали, отсутствие таблицы `pathnames`, собственный префикс
`{ru: '/rus'}`, корневой путь, query-строка.

```
сравнено локалей: 21 (совпало 21, опущено 0)
расхождений:       0
```

Проверка не вакуумная: счётчик совпадений равен 21, то есть каждый URL был
получен из заголовка и сверен, а не пропущен. Заодно видно, что случай «все
локали дают один URL» (`localePrefix: 'never'` без локализованных слагов)
корректно возвращает `undefined` — рекламировать нечего.

## 5. V22-03. Тулинг против рантайма

Свойство: тулинг и рантайм обязаны видеть один и тот же набор сообщений. Если
рантайм соберёт сообщение, которого тулинг не видел, — `typegen`, `check` и
урезанный клиентский пейлойд строятся по другому каталогу, чем тот, который
обслуживает приложение. И наоборот: текст, который парсер не смог прочитать,
обязан попасть в `junkEntries`, иначе потеря молчалива.

22 каталога: дубликаты id, placeable, два вида мусора, только атрибут, атрибут
со значением, комментарии, терм, CRLF, BOM, `select`, заглавный id, битый
placeable, id с дефисом/подчёркиванием/цифрой, пустой файл, многострочное
значение, мусор вперемешку с валидными сообщениями.

```
каталогов:                        22
id, присутствующих и там и там:   21
каталогов с junk:                  4
расхождений:                       0
```

Библиотечный `FluentBundle` минимальный — `hasMessage`, `getMessage`,
`addResource`, `formatPattern`, без `messageIds`, — поэтому рантайм
опрашивался по каждому id через `hasMessage`.

## 6. V22-04. Подозрение, которое не подтвердилось

Проверка пункта «диагностика границы не покрывает Client Component» началась с
измерения, и первое измерение выглядело как находка:

```
message: [next-fluent] Could not format message "price" (locale: en)
cause: (none)
```

Причина потеряна — ровно тот симптом, из-за которого разработчик видит «не
отформатировалось» и не видит «нет функции `BRL()`». **Находки здесь нет.**
Проверка читала `e.cause?.name`, а `cause` — это **массив** ошибок, у массива
нет `.name`. Повторное измерение:

```
message: [next-fluent] Could not format message "price" (locale: en)
cause is array? true length 1
  cause entry: ReferenceError | Unknown function: BRL()
--- дефолтный onError, то есть что реально видит разработчик ---
[next-fluent] Could not format message "price" (locale: en) [
  ReferenceError: Unknown function: BRL()
      at resolveFunctionReference (@fluent/bundle/index.js:373:31)
      …
```

Причина приложена, дефолтный обработчик печатает её со стеком. Тест № 9
закрепляет именно это — что `cause` остаётся списком и что в нём есть
`Unknown function: BRL()`. Без такого теста правка, которая заменит список на
одну ошибку или уберёт его, прошла бы незаметно.

**Две попутные ошибки в самих проверках**, обе стоили бы ложных находок, если
бы их не поймали:

- `entry.id` у `@fluent/syntax` — узел `Identifier`, а не строка. Первая версия
  сверяла `['a']` с `[{type:'Identifier',name:'a'}]` и радостно рапортовала 42
  «расхождения» в идеально работающем коде;
- `createTranslator` принимает **бандл**, а не `(locale, source)`. Первая версия
  падала с `targetBundle.getMessage is not a function`.

Общее правило из этого то же, что в V20 §7: прежде чем сообщать о расхождении,
надо убедиться, что измерительный прибор исправен.

## 7. Прочитанное без находок

- **`factory.ts` (112 строк).** `createI18n` прогоняет `validateI18nConfig`
  первым делом; `getMessages` при отсутствии `loadMessages` падает на глобальный
  request-конфиг, а не возвращает пустой каталог; `getFormatter` уважает
  настроенный `timeZone`. Замечаний нет.
- **`ftl-parse.ts` (75).** `junkEntries` корректно вытаскивает id из первой
  строки мусора; `parseFtl` превращает переполнение стека парсера в понятную
  ошибку с указанием каталога. Замечаний нет.
- **`alternate-links.ts` (138).** Вызов из `src/middleware.ts:407` передаёт
  `pathnameWithoutPrefix` — ровно то, что документирует параметр. Дедупликация
  по href и правило «x-default только если его URL уже среди уникальных»
  согласуются с V22-02.

## 8. Контрольные эксперименты

**V22-01, отрицательный контроль.** Если из `LRUCache` убрать `delete()`, тесты
№ 1 и № 2 падают (`cache.delete is not a function`); остальные шесть продолжают
проверять остальной контракт. Метод возвращён, 9/9.

**V22-02, V22-03.** Правки в `alternate-links.ts`, `route-engine.ts`,
`locale-prefix.ts`, `ftl-parse.ts` и `bundle.ts` в этом проходе не вносились:
тесты фиксируют текущее поведение, и оба содержат явные счётчики
(`compared >= 20`, `both >= 20`, `junkSeen >= 3`), чтобы проверка не могла
стать вакуумной и пройти молча.

## 9. Что осталось

1. **`catalog-io.js` — 86.21 % веток**, слабейший по веткам среди модулей
   каталога. Непокрыты строки обработчиков ошибок: `return null` в `catch`,
   `handlers.onError?.(error)`, очистка таймера. Это ветки отказов при чтении
   файловой системы — достижимы, но требуют инъекции ошибок.
2. **`cache.js:85–86`** — `console.warn` при ошибках `addResource`. Не покрыт и,
   в отличие от `warnAboutDroppedEntries`, не gated по `NODE_ENV`. С
   `allowOverrides: true` ветка почти недостижима, но несогласованность gating
   между двумя предупреждениями одного рода стоит решить в одну сторону.
3. **`server.js` 84.73 % строк** — потолок, разобран в V19.
4. **`client.js` 94.66 / 87.84** — ограничение по V15 §4, не находка.
