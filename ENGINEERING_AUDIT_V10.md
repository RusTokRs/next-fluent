## 1. V10-01 (P1). `pseudo` затирал собственные каталоги

**Воспроизведение.** CLI без единого теста; вывод писался файл за файлом.

```bash
mkdir -p messages && printf 'greeting = Hi\nbye = Bye\n' > messages/en.ftl
printf 'greeting = Привет' > messages/ru.json     # FTL в .json — портитcя
node bin/next-fluent.mjs pseudo --input messages --output messages
```

```
Error: [next-fluent] Cannot read the catalog /tmp/…/messages/ru.json: Unexpected token 'g', …
   exit=1
$ cat messages/en.ftl
greeting = [Ĥîî]
bye = [Ɓýéý]
```

Каталог `en.ftl` **перезаписан псевдолокализацией**, а ошибка в сообщении — про
`ru.json`. Пользователю сообщают о посторонней ошибке, пока его рабочие переводы
уже необратимо испорчены, а `git status` показывает правку одного файла из
двух, который он и не собирался менять.

**Почему это не «ошибка пользователя».** `--output`, совпадающий с `--input`,
выглядит как безобидная опечатка («положить туда же»), а не как команда на
перезапись. Библиотека — единственное место, где этот конфликт можно увидеть до
записи.

**Исправление.** `bin/next-fluent.mjs`: назначения вычисляются до генерации, и
если какое-либо из них совпадает с источником — команда отказывается, называя файл.

```
Error: --output would overwrite the catalog it generates from: /tmp/…/messages/en.ftl
Pick a different output directory.
```

Покрыто `test/audit-v11.test.mjs` (каталог и одиночный файл) и
`test/usage-cli.test.mjs`. На коде до правок падают **оба** теста.

## 2. V10-02 (P2). `pseudo` оставлял результат наполовину

**Воспроизведение** — тот же запуск: `en.ftl` (обрабатывается первым, файлы
собираются отсортированными) уже записан, когда `ru.json` падает.

Само по себе частичное выполнение безвредно, пока выходной каталог отличается от
входного, — но в сочетании с V10-01 оно и дало «ошибку про `ru.json` при
испорченном `en.ftl`»: два независимых дефекта складывались в одно сообщение,
уводящее от причины.

**Исправление.** Всё генерируется в памяти, запись начинается только после
успешного чтения всех каталогов. Проверено: при битом `ru.json` выходной каталог
даже не создаётся, источники не тронуты. Команда стала «всё или ничего».

## 3. V10-03 (P1). Определение локали на сервере не проверялось нигде

§12 V9 поставил это первым. Разбор показал двойную причину:

1. `await import('next/headers.js')` в Node бросает исключение, и `catch` в
   `getLocale()` съедает его как «запроса нет» — ветка недостижима by design.
2. В Next-фикстуре все страницы лежат под `app/[locale]/`, а layout вызывает
   `setRequestLocale`. Значит `store.locale` всегда задан и `getLocale()` выходит
   раньше, не дочитывая ни cookie, ни `Accept-Language`.

То есть четыре ступени приоритета (заголовок → cookie → `accept-language` →
по умолчанию) не были проверены ни разу за всё существование проекта.

**Исправление — в фикстуре, а не в harness'е.** Node-harness не воспроизводит
request scope React'а честно; фикстура — единственное место, где он существует.

- `test/fixtures/next-app/app/probe/page.tsx` — маршрут с
  `dynamic = 'force-dynamic'`, который **не** вызывает `setRequestLocale` и
  рендерит `getLocale()`, `getNow()`, `getTimeZone()`, `getFormats()`,
  `formatter.number()`, переводы и заголовки запроса в атрибуты `data-probe-*`.
- `test/fixtures/next-app/app/probe/layout.tsx` — собственный root layout без
  `setRequestLocale`, импортирующий новый `i18n/server-config.ts`.
- `test/fixtures/next-app/middleware.ts` — `/probe` исключён из matcher'а, иначе
  локаль всегда приходила бы заголовком middleware и первая ступень выигрывала
  бы всегда; проверка была бы зелёной и бессмысленной.
- `test/fixtures/next-app/i18n/server-config.ts` — `configureServerI18n({
  locales: ['en','ru'], defaultLocale: 'en' })`. Без списка локалей
  `Accept-Language` не используется вовсе (см. V10-04).
- `scripts/test-next-integration.mjs` → `checkLocaleDetection()`: матрица из семи
  строк в порядке приоритета, каждая проверяет и локаль, и то, что конфиг
  запроса уже загружен (по фиксированным `now`/`timeZone` из конфига), плюс две
  параллельные проверки на то, что store не шарится между запросами.

Сравнение HTML вырезает U+2068/U+2069 — это bidi-изоляция Fluent, а не данные.

**Отрицательный контроль.** Мутация чтения заголовка (`headerStore.get(
`${headerKey}-mutated`)`) — семантическая, типы проходят:

```
Error: Locale detection: the forwarded header beats the cookie rendered without data-probe-locale="ru"
   exit=1
```

Первая проба контроля была мутацией `if (false && validHeaderLocale)`, и она
**упала на `tsc`, а не на гейте** — то есть проверку не достигла. Это зафиксировано
как правило метода: отрицательный контроль должен ломать проверяемую логику, а не
компиляцию.

## 4. V10-04 (P2). `configureServerI18n` не документирован

Экспорт есть в `next-fluent/server`, он решает, будет ли `getLocale()` вообще
учитывать `Accept-Language` (без списка локалей нечего выбирать, и предпочтение
браузера молча игнорируется, а каждый запрос падает в локаль по умолчанию) — и его
нет в README. При этом вызвать его надо **до первого** `getLocale()` запроса, то
есть не из `request.ts` (он резолвится этими же хелперами) и не из
`routing.ts` (его импортирует клиент). Это ровно тот случай, когда отсутствие
документации выглядит как «библиотека не работает».

**Исправление.** README, раздел 4 (рядом с middleware), подраздел «Telling the
server which locales exist»: код примера, оба запрещённых места и объяснение
симптома без вызова.

## 6. CLI: пути, с которых начинается работа

Отдельный обзор `bin/next-fluent.mjs` показал, что весь файл покрыт сценариями,
которые начинаются с `check --input … --src …`. То, что человек запускает первым,
не проверено: без аргументов, `--help`, опечатка в команде, несуществующий путь,
каталог, который не найден, автообнаружение `messages/` и `src/messages/`. Всё это
работало — теперь это закреплено (`test/usage-cli.test.mjs`, +8 тестов), покрытие
файла выросло с 70.3 % до **78.2 %** по ветвям.

Непокрытым остался блок `--watch` (строки 150-180): он блокирует процесс, и
тест на нём означал бы гонку и таймаут вместо проверки. Это осознанно оставлено.

## 7. Что проверено и оказалось в порядке

- **Цепочка fallback-локалей** приоритет по списку, `fallbackLocale` выше
  `fallbackLocales`, `null`/`''` пропускаются, несуществующая локаль не ломает
  поиск, последний резерв — сам ключ.
- **`CURRENCY`/`PERCENT` с нечисловым аргументом** — возвращается исходный текст.
- **CLI без аргументов / `--help` / опечатка** — сообщения называют проблему и
  печатают usage; коды выхода 1 / 0 / 1 / 1.
- **Автообнаружение каталогов** — `messages/` и `src/messages/`; сообщение при
  отсутствии перечисляет, где искали, и предлагает `--input`.
- **`runtime.getMessages`** — возвращает каталог из request config; при
  `loadMessages` конфигурации приоритет отдаётся загрузчику, который вызывается
  один раз с разрешённой локалью.
- **Побочный эффект V10-01 уже не воспроизводится**: источник и цель совпадают в
  четырёх формах (каталог, одиночный файл, абсолютный путь, `./`-форма) — отказ
  единообразный.

## 9. Приоритеты следующего прохода

1. **`catalog-io.js` (77.6 % ветвей)** — непокрыты `walk` при ошибке,
   `catalogSnapshot`, ветки `watchCatalogs`. Последнее стоит отдельно: файловый
   наблюдатель — единственная подсистема, у которой нет теста на
   «дождался/не дождался изменения».
2. **`client.js` (70.2 %)** и **`navigation.js` (59.5 %)** — ветви, требующие
   браузерного контекста; разбирать по одной, начиная с тех, что не требуют DOM.
3. **`server.js` (84.2 %)** — остаток приходится на ветки, живущие только в
   Next-запросе; закрывать в фикстуре, не в Node-harness.
4. **`--watch` в CLI** — если захочется закрыть, способ должен быть без гонок:
   сначала тест на «наблюдатель пережил переименование файла», и только потом
   тест на само наблюдение.
