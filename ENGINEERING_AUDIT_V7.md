## 2. V7-01. Браузерный путь каталога молчал о выброшенных записях (исправлено)

Проход V6 сделал серверный рантайм честным: `src/catalog-integrity.ts` сверяет
объявленные в каталоге записи с теми, что остались в `FluentResource`, и один
раз на каталог называет потерянные id. Клиентский `FluentProvider` строит
бандл из того же каталога своим путём (`createFluentBundle`), и там тот же
класс ошибки оставался невидимым: сообщение со синтаксической ошибкой парсер
выбрасывает без предупреждения, а UI рисует ключ.

```tsx
// до правок: рендерится "broken-v7-01", в консоли ни слова
<FluentProvider locale="en" messages={'ok = Fine\nbroken = { $x -> [one] one }'}>
  <FormattedMessage id="ok" />
</FluentProvider>
```

**Исправление.** `FluentProvider` вызывает `warnAboutDroppedEntries()` для
основного и для fallback-каталога, но только когда
`process.env.NODE_ENV !== 'production'`. Серверная политика осталась прежней
(предупреждение всегда: там каталог парсится для всех запросов, и строка в
продовом логе actionable). Оба вызова делят один экземпляр модуля и один
`warnedCatalogs`, поэтому каталог, разобранный и на сервере, и в браузере,
предупреждает один раз.

Почему именно так, а не «подключить модуль в клиентский граф»:

| | |
| --- | --- |
| Стоимость в development | **976 B** min (весь модуль + два вызова) |
| Стоимость в production | **0 B** — `process.env.NODE_ENV` заменяется литералом всеми бандлерами, которые собирают браузерные бандлы (Next.js/webpack/Turbopack, Vite, esbuild); ветка становится недостижимой, а импорт модуля — неиспользуемым |
| Проверка, что это не сломается | `npm run size` собирает ту же фикстуру ещё раз с `NODE_ENV=development` и **падает**, если разница меньше 256 B — то есть если сканирование когда-нибудь окажется вне guard’а |

Бандлер, который не подставляет `process.env.NODE_ENV`, оставит проверку в
бандле — это безопасное направление отказа, и оно записано в комментарии.

## 3. V7-02. Бюджет клиента измерял фасад, а не то, что грузит браузер (исправлено)

Приоритет №1 V6 звучал как «следующая правка клиентского графа потребует
поднять бюджет или сузить корневой энтри». Ни то, ни другое не понадобилось:
`scripts/size-budget.mjs` собирал **пакетный корень** (`src/index-browser.ts`) —
фасад, который реэкспортирует `client`, `navigation`, `routing`, `bundle`,
`utils`, `catalog` и две функции, — и потому считал байты, которые приложение
выбрасывает при tree-shaking’е. Замеры на одной и той же ревизии:

| Что собирается | minified | gzip |
| --- | --- | --- |
| корневой агрегатный энтри (как мерилось) | 48.7 kB | 16.6 kB |
| поверхность клиента, которую импортирует приложение (фикстура) | **47.1 kB** | **15.9 kB** |
| то же без `@fluent/bundle` (свой код) | 36.3 kB | 12.3 kB |

Лишние ~1.6 kB — ровно те экспорты, которые не вызывает ни один компонент
(`resolveAcceptLanguage`, `jsonToFluent`, `validateI18nConfig`, `LRUCache`,
`createDefaultFunctions` и т. д.). Три прохода подряд бюджет поднимался на
0.5 kB, потому что рос прокси-замер; продуктовая величина при этом росла не
обязана.

**Исправление.**

- Бюджет собирает `test/fixtures/size/client-consumer.ts`, который импортирует
  **весь документированный клиентский API через опубликованные спецификаторы**
  (`next-fluent`, `next-fluent/client`, `next-fluent/navigation`,
  `next-fluent/routing`) — то есть проходит тот же `exports`-мэп, что и
  потребитель, и собирается по `dist/`.
- Бюджеты пересчитаны по замеру и **опущены**: 49.0 → **47.5 kB** min,
  17.0 → **16.25 kB** gzip; свой код 38.5 → **36.75 kB** / 13.25 → **12.75 kB**.
  Запас остался соразмерным прежнему (0.4 kB min ≈ 0.85 %), но теперь он
  отсчитывается от реально скачиваемой величины.
- `npm run size` собирает `dist/` перед замером (`package.json`) — фикстура
  резолвится через `exports`-мэп, значит обязана видеть свежую сборку.
- Инвариант «фикстура — это определение клиентского бандла» проверяется тестом:
  он берёт рантайм-экспорты `dist/client.js` и `dist/navigation.js` и падает,
  если новый экспорт не добавлен в фикстуру (иначе бюджет молча перестал бы его
  считать).

Честная оговорка: выигрыш скромнее, чем можно было ожидать (1.6 kB min, а не
несколько килобайт) — потому что почти весь агрегат и так нужен странице.
Ценность не в выигрыше, а в том, что число бюджета теперь означает «столько
скачает посетитель», и расти оно может только по делу.

## 4. V7-03. V5-06: пунктирный ключ — зафиксированное правило, а не долг (закрыто без правок кода)

V6 §8 держал V5-06 вторым приоритетом: «атрибут по-прежнему недостижим через
`t()`, правило разрешения придётся пересматривать вместе с форматом ключей».
Разбор показал, что пересматривать нечего:

- **В Fluent пунктирного id не существует.** Идентификатор сообщения —
  `[a-zA-Z][a-zA-Z0-9_-]*`; `greeting.formal` в FTL — это всегда сообщение
  `greeting` и его атрибут `formal`. Дефисную форму `greeting-formal` добавляет
  наша конвенция JSON-каталогов (`{ greeting: { formal } }`).
- **Конфликт двух значений одним ключом не разрешается никаким порядком.**
  Если в каталоге есть и сообщение `greeting-formal`, и атрибут `.formal` у
  `greeting`, то любой порядок кандидатов делает одно из них недостижимым
  *через пунктирную запись* — но не вообще: доступ остаётся у обоих
  (`t('greeting-formal')` и `t.attrs('greeting').formal`), и именно этот
  «дефис раньше пунктира» порядок описан в README (§JSON-каталоги) и повторён
  `typegen`’ом из V5-06.
- Поэтому правильный ответ — не менять приоритет (это просто переложило бы
  затенение на JSON-каталоги), а **зафиксировать** оба доступа тестом.

Новый тест `V5-06: a message shadowing an attribute is reachable both ways`
проверяет четыре утверждения: `t('greeting.formal')` и `t('greeting-formal')`
дают сообщение, `t.attrs('greeting')` даёт атрибут, `t.has('greeting.formal')`
— `true`, и что при отсутствии затеняющего сообщения пунктирная запись
разрешается в атрибут.

## 5. V7-04. Workflow публикации: что удалось проверить вживую

1. **Статическая проверка.** Оба workflow прогнаны через `actionlint`
   (npm-пакет `actionlint@2.0.6`, wasm-сборка Go-линтера): `ci.yml` — 0 находок,
   `publish.yml` — 0 находок, включая выражения `if:` и обращения к
   `inputs.dry-run`. Побочный вывод: линтер в CI пока не заведён — пакет
   упаковывает `actionlint-v0.0.0`, версия внутри не совпадает с версией
   пакета, и делать его devDependency ради одной проверки в этом проходе
   неоправданно; проверка выполнена разово и записана здесь.
2. **Dry-run целиком.** `npm publish --dry-run` — та самая команда, которую
   запускает workflow, — прогнан локально после коммита. Он выполняет
   `prepublishOnly` → `npm run check` → `prepack` → `npm run build` → сборку
   тарбола, поэтому проверяет ровно тот путь, которым пакет уходит в реестр.
3. **Найденный факт: гейт выполняется дважды.** Шаг `Run the full check` в
   workflow и `prepublishOnly` внутри `npm publish` — это один и тот же
   `npm run check`. Осознанно оставлено и задокументировано прямо в workflow:
   явный шаг делает падение видимым шагом, а запуск на этапе `publish` —
   гарантирует, что тарбол собран из проверенного дерева (`prepack` → build) и
   что `--ignore-scripts` нельзя добавить «для скорости». Цена — один
   повторный прогон батареи на релиз.
4. **Чего сделать нельзя до мержа.** `workflow_dispatch` доступен только для
   workflow, существующего в ветке по умолчанию. Факт проверен:

   ```
   $ gh api repos/RusTokRs/next-fluent/actions/workflows --jq '.workflows[].name'
   CI
   $ gh workflow run publish.yml
   HTTP 404: Not Found (https://api.github.com/repos/RusTokRs/next-fluent/actions/workflows/publish.yml)
   ```

   То есть первый живой dispatch `publish.yml` возможен ровно после того, как
   PR #7 попадёт в `main`; это ограничение GitHub, и оно записано здесь, чтобы
   не искать его повторно. Всё, что можно проверить до этого момента (YAML,
   выражения, команды, упаковку), — проверено.

## 5a. V7-05. Dry-run публикации ломал интеграционный прогон (исправлено)

Пункт 4 из §5 проверялся не «чтением», а запуском: `npm publish --dry-run`
действительно выполняет `prepublishOnly` → `npm run check` → `prepack` →
сборку тарбола — и **первый же запуск упал**:

```
added 54 packages in 2s
Error: ENOENT: no such file or directory, open
  '/home/user/next-fluent/.next-integration-5871/node_modules/next/package.json'
    at readFileSync (scripts/test-next-integration.mjs:254:34)
```

Причина — наследование окружения. npm передаёт свою конфигурацию скриптам в
виде `npm_config_*`, а `npm publish --dry-run` добавляет туда
`npm_config_dry_run=true`. Harness интеграционного прогона запускает вложенный
`npm install` с `env: { ...process.env, … }`, и для вложенного npm это тоже
dry-run: команда **рапортует об успехе, ничего не записывая**. Механизм
воспроизведён отдельно, в одну строку:

```
$ npm_config_dry_run=true npm install --no-save lodash
add lodash 4.18.1
added 1 package in 337ms
$ ls node_modules | wc -l
0
```

То есть «нулевая» установка видна только через несколько шагов, как `ENOENT`
на `package.json` — в стороне от причины. Именно этот путь проходит
**документированный первый прогон workflow** (ручной dispatch по умолчанию —
dry-run), так что дефект был не теоретический: PR #7 не смог бы отрепетировать
релиз.

**Исправление.**

- `scripts/npm-env.mjs` — `cleanNpmEnv()` убирает из дочернего окружения весь
  namespace `npm_config_*` (регистронезависимо: в CI встречается
  `NPM_CONFIG_*`) и сохраняет всё остальное; `inheritedNpmConfigKeys()` отдаёт
  список унаследованных ключей.
- `scripts/test-next-integration.mjs` — все три дочерних процесса (установка
  Next, `next build`, `next start`) стартуют с `cleanNpmEnv(…)`; после установки
  добавлена явная проверка, что `node_modules/next/package.json` появился, — с
  сообщением, называющим унаследованные ключи, вместо `ENOENT` через три шага.
- `scripts/test-domain-browser.mjs` — тот же класс (вложенный `npm install` для
  Next 16 и `openssl`): `run()` по умолчанию получает `cleanNpmEnv()`.
- Инвариант закреплён тестами: `cleanNpmEnv` вычищает namespace и сохраняет
  посторонние переменные, а оба harness-скрипта не содержат `...process.env`
  (иначе утечка вернётся).

**Проверка.** После исправления `npm publish --dry-run` прошёл целиком: полный
гейт (включая `test:next` и `test:next:16` со вложенной установкой Next 16) и
сборка тарбола — 114 файлов, 155.6 kB в архиве, 608.8 kB распакованных;
`dist/index.js` исключён, `README.md`, `LICENSE`, `bin/next-fluent.mjs` и
`plugin.d.cts` на месте.

## 7. Приоритеты для следующего прохода

Открытых дефектов в этом проходе нет; всё, что найдено, закрыто кодом или
замером. Что остаётся для следующего:

1. **Первый живой `workflow_dispatch publish.yml` — после мержа PR #7.** До тех
   пор «вживую» проверены YAML, выражения, команды и упаковка, но не сам запуск
   workflow на раннере GitHub. Локальный dry-run теперь проходит целиком
   (§5a), так что этот шаг остаётся проверкой раннера, а не сценария.
2. **Браузерные прогоны в песочнице недоступны** (нет Chromium):
   `test:next:browser` и `test:next:domains` подтверждаются только CI.
3. **Завести `actionlint` в CI** — когда (и если) пакет начнёт публиковать
   версию, совпадающую с содержимым: сейчас `actionlint@2.0.6` везёт
   `actionlint-v0.0.0`, и делать это devDependency ради одной проверки рано.
4. **Клиентский бюджет: следующий шаг — не поднимать.** Запас 0.4 kB min
   (0.85 %) и 0.35 kB gzip; если очередная правка клиентского графа его
   исчерпает, решение (вынести `resolveAcceptLanguage`/`jsonToFluent` из
   корневого энтри или признать рост) стоит принимать по факту, а не заранее:
   теперь бюджет измеряет именно скачиваемое, и рост в нём означает реальную
   цену для посетителя.
