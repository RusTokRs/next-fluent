## 2. P1 — инструменты: ложные срабатывания `check --usage` (исправлено)

### V4-01. `t.raw(key)` был невидим для анализатора использования → ложный «unused»

`CALL_METHODS` в `src/usage.ts` перечислял `rich`, `attrs`, `plain`, `markup`,
`has`, `exists` — **без `raw`** (при этом `markup` и `exists` в API библиотеки
вообще не существуют). Ключ, который приложение читает только через `t.raw()`,
попадал в отчёт как мёртвый, а с `--strict-usage` это валило команду.

Репро (до правки):

```
messages/en.ftl:  list = ["a","b"]
src/page.tsx:     const t = useTranslations(); const items = t.raw("list");
$ next-fluent check --input messages --reference en --usage --src src --strict-usage
unused (1)
  "list" is defined in en but never referenced in the scanned sources.   ← ложь, exit 1
```

Исправлено: `raw` добавлен в список методов; для метода `raw` (как и для
`attrs`) атрибуты сообщения без значения помечаются использованными — рантайм
возвращает именно их список.

### V4-02. `t.plain(key)` требовал атрибутов → `check --usage` падал на документированном применении

Проверка была `attrs || plain → у сообщения должны быть атрибуты`. Но
`t.plain()` форматирует **значение** сообщения, а атрибуты не читает вовсе:
`t.plain('rich')` для `rich = Click <b>here</b>` — это ровно тот сценарий, для
которого метод и документирован в README. `missing-attributes` — «жёсткая»
находка, поэтому `check --usage` завершался с кодом 1 на корректном коде.

Репро (до правки):

```
messages/{en,ru}.ftl:  rich = Click <b>here</b> / Cliquez <b>ici</b>
src/page.tsx:          const label = t.plain("rich");
$ next-fluent check --input messages --reference en --usage --src src
[next-fluent] Checked 2 catalog(s) against "en" (3 keys).
[next-fluent] No issues found.            ← каталоги в порядке
missing-attributes (1)
  t.plain("rich") was called, but "rich" defines no attributes.   ← ложное, exit 1
```

Исправлено по существу, а не отключением проверки:

* `attrs` — по-прежнему требует атрибутов;
* `plain` больше не требует атрибутов;
* вместо этого введён набор `attributeOnly`: сообщение, у которого есть только
  атрибуты, **адресуемо** для `t.attrs()`/`t.raw()` (так работает рантайм) и
  **не адресуемо** для `t()`/`t.rich()`/`t.plain()`. Для последних теперь
  выдаётся точный `missing-attributes` («defines only attributes and no value»),
  а не ложное «ключ отсутствует в каталоге» — раньше `t.attrs('attr-only')`
  давал именно жёсткую ошибку `missing`;
* `t.plain('msg.attr')` (обращение к атрибуту через точечный путь — рантайм это
  поддерживает) не флагуется.

README-таблица находок приведена в соответствие:
`t.attrs(k)` — нет атрибутов, `t.plain(k)` — нет значения.

После правки: `3/3 keys used`, `exit 0` на том же проекте, и с `--strict-usage`
тоже.

## 3. P2 — архитектура и функциональные пробелы (исправлено)

### V4-03. `tFn.attrs` и `tFn.plain` определялись дважды (исправлено)

В `src/bundle.ts` было **две** присваивания `tFn.attrs` (было: строки 440 и 511)
и **два** `tFn.plain` (495 и 569). Вторая версия молча побеждала, первая была
мёртвым кодом — причём версии `attrs` различались: у первой не было
fallback-поиска по kebab-ключу. Класс ошибки — неудачное слияние: любая будущая
правка «верхней» копии была бы no-op без единого симптома, а лишние ~90 строк
уезжали в `dist` и в npm-пакет.

Исправлено: удалены первые (мёртвые) определения, оставлены действующие.
Добавлен сторожевой тест: каждый метод `tFn.*` определяется ровно один раз.

### V4-04. `t.has()` и `<FormattedMessage fallback>` расходились на сообщениях без значения (исправлено)

`has()` отвечал через `bundle.hasMessage(id)`, который возвращает `true` и для
сообщения с одними атрибутами, тогда как `t()/t.rich()` такое сообщение
отформатировать не могут. `<FormattedMessage>` решает по `has()`, рендерить ли
`fallback`, поэтому `fallback` **молча игнорировался** и на страницу попадал
сырой ключ.

Решение: `has()` теперь отвечает ровно на вопрос «отрендерит ли `t(key)` что-то»
и повторяет обход кандидатов самого `t()`: значение сообщения → `true`, путь к
атрибуту → `true`, id с одними атрибутами и отсутствующие ключи → `false`.
Атрибутные пути остаются запрашиваемыми — именно их рендерят
`t.attrs()`/`t.plain('id.attr')`.

Проверено (SSR + юнит-уровень):

```
t.has('full')             true     t('full')            "Text"
t.has('attr-only')        false    t('attr-only')       "attr-only" (+ MISSING_MESSAGE)
t.has('attr-only.label')  true     t('attr-only.label') "L"
t.has('missing')          false

<FormattedMessage id="attr-only" fallback="FB" />  → "FB"      (было "attr-only")
<FormattedMessage id="full"      fallback="FB" />  → "Text"
<FormattedMessage id="missing"   fallback="FB" />  → "FB"
```

`t.has()` вообще не был документирован — добавлен в README с этой семантикой.

### V4-05. Заголовок `x-next-fluent-rewrite` подделывался клиентом (исправлено)

Сначала — измерение. Временный флаг, отключающий проверку сигнала, прогнан на
**реальном приложении-фикстуре** (Next 15.5.26 и 16.3.8): без сигнала
`/about-us` отвечает `307 → /about-us` бесконечно, `/` и `/en` — так же; дамп
заголовков показал, что вторая итерация middleware выполняется **в том же
процессе** и получает заголовки, приложенные первым проходом к рерайту. То есть
сигнал — не «подстраховка», а единственная причина, по которой localized-slug
маршруты вообще открываются.

Решение: сигнал связан со **случайным токеном процесса**
(`x-next-fluent-rewrite-token`, `crypto.randomUUID()` при загрузке модуля).
Вторая итерация несёт оба заголовка и распознаётся как фиксированная точка;
клиент, угадавший только путь, получает канонический редирект. Внутренние
заголовки не доходят до приложения: на фиксированной точке middleware снимает
их перед передачей в маршрут.

| Сценарий (`/en/about` — внутренний алиас канонического `/about-us`) | до | после |
| --- | --- | --- |
| документная навигация | 307 → /about-us | 307 → /about-us |
| + `x-next-fluent-rewrite: /en/about` | **200 (обход)** | **307 → /about-us** |
| + заголовок и чужой токен | не проверялось | **307 → /about-us** |
| вторая итерация (реально переданные заголовки) | 200 | 200 |
| `sec-fetch-dest: empty` (router fetch) | 200 | 200 — см. ниже |
| `/ru/o-nas`, `/about-us`, `/` | 200 | 200 |

Остаточный случай — `sec-fetch-dest`: это метаданные, которые ставит сам
браузер, и недокументные запросы к внутреннему алиасу по-прежнему обслуживаются
без канонизации. Так требует клиентский роутер Next 16: после рерайта он сам
идёт за внутренний путь (в дампе это `307 → /en/about?_rsc=…`, затем fetch с
`sec-fetch-dest: empty`). Полностью закрыть случай нельзя, не сломав
клиентские переходы; важно, что теперь **документные** навигации (поисковики,
переходы по ссылкам, прямые заходы) канонизируются независимо от того, какие
заголовки прислал клиент, а недокументный ответ — это RSC-фрагмент, а не
индексируемая страница. Комментарий в коде и `SECURITY.md` приведены в
соответствие с этим поведением; `CHANGELOG.md` описывает изменение.

Регрессии: 4 теста в `test/audit-v4.test.mjs`, а тесты второй итерации в
`test/audit-v3.test.mjs` (`V3-02`, `V3-06c`) и
`test/domain-prefixes.test.mjs` теперь воспроизводят реальный контракт — берут
заголовки из первого ответа (`response.request.headers`) и переигрывают их,
вместо того чтобы подставлять константы.

## 4. P3 — качество инструментов, документации и гигиена

### V4-06. Лишний хоп редиректа при согласовании по `Accept-Language` (исправлено)

`/about-us` с `accept-language: ru` → 307 `/ru/about-us` → 307 `/ru/o-nas`:
ветка «preferred locale — не дефолтная» (`src/middleware.ts:468-470`) не
канонизирует слаг, в отличие от соседних веток (там вызывается
`canonicalPath`). Достаточно применить `canonicalPath(preferredLocale, pathname)`.
Не исправлено, потому что текущее поведение **зафиксировано тестами**
(`test/audit-v3.test.mjs:274-280`, `:442-443`) — это осознанное решение, а не
случайность; менять его стоит вместе с тестами.

### V4-07. `check` принимает имя файла за локаль (исправлено)

`readCatalogsByLocale` (`src/catalog-io.ts:69-86`) в плоской раскладке считает
локалью каждое имя файла, поэтому `messages/en-app.json` становится «локалью»
`en-app` и, будучи первым по алфавиту, автоматически делается **референсной
локалью**. Воспроизведено на минимуме — `messages/{en.ftl,ru.ftl,en-app.json}`,
где `en-app.json` содержит один ключ `app-title`:

```
[next-fluent] Checked 3 catalog(s) against "en-app" (1 keys).
  en:
    [missing] "app-title" is missing.
    [extra] "hello" does not exist in en-app.
  ru:
    [missing] "app-title" is missing.
    [extra] "hello" does not exist in en-app.
[next-fluent] 4 issue(s) found.
```

То есть `check` сравнивает FTL-локали с JSON-файлом, который локалью не
является, а в выводе нет ни слова о том, что найден «locale» `en-app`; `typegen`
и `pseudo` при этом сливают все файлы в один каталог — несогласованность.
Рекомендация: валидировать имена локалей (BCP-47) и/или поддержать
`‹locale›-‹namespace›.ftl`, либо предупреждать, что раскладка «один файл на
локаль» обязательна.

### V4-08. Нет `Vary: Accept-Language` на ответах, зависящих от заголовка (исправлено)

`GET /` в `as-needed` отдаёт 307 на `/ru` при `Accept-Language: ru` и 200
(rewrite на `/en`) при `en`, и ни один из ответов не содержит `Vary`. При
CDN-кешировании редиректа это классическое «первый посетитель определяет язык
для всех». Рекомендация: `Vary: Accept-Language` (и, если решает cookie,
продумать `Cache-Control`), либо `localedDetection: false` для кешируемых зон.

### V4-09. `Host` влияет на `Location` при незаданном `trustedHosts` (исправлено предупреждением)

```
Host: evil.example  → 307 Location: http://evil.example/en/x
```

`SECURITY.md` описывает это как защищённый случай («redirect targets come only
from the trusted `domains` config or the request's own origin»), README:245
рекомендует `trustedHosts` — и он действительно отклоняет чужой `Host` (`421`),
— но защита opt-in, а без неё «own origin» — это и есть заголовок `Host` из
запроса. По умолчанию в `always`/`as-needed` редиректы выпускаются по нему.
Рекомендация:
предупреждать в dev-режиме, когда `trustedHosts` не задан и middleware
собирается выпустить редирект; либо включать строгий режим при `NODE_ENV !==
'production'`.

### V4-10. Cookie локали по умолчанию без `Secure` (исправлено)

`resolveCookieConfig` (`src/middleware.ts:64-80`) дефолтит `path/maxAge/
sameSite`, но не `secure` — на HTTPS-сайте cookie уходит и по HTTP. В README
пример с `secure: true` есть, в дефолтах — нет. Cookie не секретна, но
`secure: true` — современный дефолт; как минимум стоит упомянуть в README, что
его нужно задать.

### V4-11. Документация: две неточных формулировки (исправлено)

* «the locale cookie is only written on document requests **when it actually
  changes**, so static pages stay CDN-cacheable» (README:18). Код ведёт себя
  именно так: запись происходит, когда определённая локаль отличается от
  отсутствующей/cookie (`GET /en/about` без cookie → `Set-Cookie NEXT_LOCALE=en`).
  Но «CDN-cacheable» верно лишь для уже имеющейся cookie: первый ответ каждому
  клиенту всё равно несёт `Set-Cookie`, а `Vary` (V4-08) не выставляется —
  формулировке не хватает этой оговорки.
* «(including `x-default`) for every localized route» (README:19) — при заданных
  `domains` `x-default` не выпускается вовсе (`src/alternate-links.ts:102`);
  в детальном разделе (README:489) оговорка есть, в буллете — нет.

### V4-12. `formatUrlObject` молча игнорирует поля `UrlObject` (исправлено)

`{ href: '/x' }` → `/`; `{ hostname: 'evil.example', pathname: '/x' }` → `/x`;
`protocol`/`host`/`auth`/`slashes` не учитываются. Next.js-объект `Url` эти поля
использует, поэтому миграция может молча получить другую ссылку. Рекомендация:
бросать ошибку на непустые `host`/`hostname`/`protocol`/`auth` (или поддержать
`href` как источник пути).

### V4-13. Инлайн-объект `functions` у `FluentProvider` пересобирает бандл каждый рендер (исправлено)

`useMemo` зависит от ссылки `functions` (`src/client.ts:141`), а `functions`
попадает в `getCachedFluentBundle`, где при непустом наборе **кеш отключён**
(`cache.ts`) — то есть `functions={{...}}` в разметке провайдера означает
повторный парсинг FTL и новый bundle на каждый рендер (и перерисовку всех
детей, т.к. меняется значение контекста). Ошибки тут нет, но ловушка
производительности; помогает memo у потребителя или хеширование набора ключей.

### V4-14. Alternate links сохраняют route-параметры в query (исправлено)

`buildAlternateLinksHeader` копирует `search` как есть
(`src/alternate-links.ts:89`), тогда как `resolveLocalizedPathname` вычищает из
query параметры, которые были поглощены маршрутом (`src/nav-url.ts:210-214`).
Воспроизведено на `pathname: '/dokumenty/7', search: '?id=7'`:

```
Link: <…/docs/7?id=7>; hreflang="en", <…/ru/dokumenty/7?id=7>; hreflang="ru",
      <…/docs/7?id=7>; hreflang="x-default"
resolveLocalizedPathname('/docs/7?id=7', ru) → '/ru/dokumenty/7'   (без ?id=7)
```

`id` уже поглощён маршрутом, поэтому в `Link`-заголовке он — дубль. Влияние —
SEO-шум, безобидно, но несогласованно.

Здесь же замечено: в `never`-режиме без `domains` и без локальных слагов все

### V4-17. `watchCatalogs` молча не следит ни за чем на Node 24 и Windows (исправлено)

Найдено матрицей CI после первых правок прохода: 6 из 8 ячеек упали на шаге
`npm test`, при этом ubuntu + Node 22 проходили. Причина — платформенное
поведение `fs.watch`:

```
node 22, Linux:  fs.watch('/missing', {recursive:true})  →  sync throw ENOENT
node 24, Linux:  fs.watch('/missing', {recursive:true})  →  watcher без ошибки
                 и без единого события (проверено 500 мс)
```

`watchCatalogs` полагался на синхронный throw, поэтому на Node 24 (и на
Windows, где поведение такое же) `next dev` получал watcher, который никогда
не срабатывает и ничего не сообщает: типы просто перестают перегенерироваться.
Хуже того, у созданного watcher'а не было обработчика `'error'` — асинхронная
ошибка (каталог удалили, исчерпан inotify) убивала процесс как uncaught
exception.

Исправление: путь проверяется через `fs.statSync(input, { throwIfNoEntry: false })`
до `fs.watch`, отказ уходит в `onError` (тот самый колбэк, который уже
передают и плагин, и CLI) с сообщением, называющим каталог; на созданный
watcher навешивается `'error'`. Проверено на Node 22 и Node 24 (376/376 в
обоих) и матрицей CI.
