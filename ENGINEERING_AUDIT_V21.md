## 3. V21-01. Провайдер роняет четыре категории, а говорит об одной

V20 добавил в `FluentServerProvider` предупреждение о собственных
Fluent-функциях. Измерение того же места с более полным конфигом показало, что
функции — лишь первая из четырёх категорий, которые через границу не проходят:

```
  messages                 forwarded  "hi = Hi { $name }\n"
  functions                DROPPED    —            ← V20 предупреждал
  defaultTranslationValues forwarded  ["name"]     ← колбэк rich удалён молча
  onError                  DROPPED    —            ← молча
  getMessageFallback       DROPPED    —            ← молча
  useIsolating             forwarded  false
  timeZone                 forwarded  "UTC"
```

То есть V20 закрыл четверть проблемы. Остальные три вели себя хуже функций,
потому что про них не было даже намека:

- **колбэки в `defaultTranslationValues`.** Строковые значения переходят,
  функции отфильтровываются (`typeof value !== 'function'`). Фильтр правильный —
  сериализовать функцию нельзя. Но сообщение с `{rich}` на сервере рендерится
  колбэком, а в Client Component теряет его, и никто не говорит почему;
- **`onError`.** На клиенте работает клиентский обработчик (или дефолтный
  `console.error`), серверный остаётся на сервере. Ошибки перевода на двух
  сторонах уезжают в разные места;
- **`getMessageFallback`.** Клиент печатает дефолтный фолбэк `locale:key` вместо
  настроенного — то есть ровно тот симптом, ради которого фолбэк и настраивали.

**Исправление.** Диагностика собирает все четыре категории и говорит один раз:

```
[next-fluent] <FluentServerProvider> cannot forward Fluent function "BRL", callback
defaultTranslationValues "rich", `onError` and `getMessageFallback`: a function is
code, so it cannot cross the Server Component boundary. Client Components will not
format these messages the way the server does. Define them on a `<FluentProvider …>`
inside a `'use client'` wrapper as well.
```

Одно предупреждение на границу, а не четыре подряд: это одна причина (функция не
сериализуется) и одно решение (определить на клиентской стороне). В production
ветка недостижима, как и раньше. Конфиг без функций не предупреждает вовсе —
тест № 3 проверяет и это, и заодно что сериализуемое (`useIsolating`, `timeZone`,
строковые значения) по-прежнему переходит.

## 4. V21-02. Круговая пара префиксов под фаззингом

`prefixForLocale` строит префикс локали для URL, `matchLocalePrefix` разбирает
путь обратно. Свойство, которое они обязаны держать совместно: для любого
конфига, прошедшего валидацию, `matchLocalePrefix(prefixForLocale(L) + rest)`
возвращает `L` и `rest`.

Прогон: 6 наборов локалей (включая `['EN','en']`, `['en-US','en']`,
`['en','ru','ru-RU']`) × 18 таблиц префиксов × 4 режима × 11 форм пути
(двойные слеши, хвостовой слеш, процентное кодирование, юникод, пробел, точки,
регистр).

```
круговых проходов:                 2552
конфигов, отвергнутых валидатором:  328
отказов кругового прохода:            0
утечек валидатора:                    0
```

Вторая цифра важнее первой. Круговой проход имеет смысл только для конфигов,
прошедших валидацию, поэтому настоящий вопрос — **не нормализует ли какая-то
публичная точка входа префиксы в обход валидации**. Все 328 отвергнутых
`validateLocalePrefix` конфигураций отвергает и `defineRouting`: ни одна
некорректная форма до матчера не доходит. Тест № 6 закрепляет это как гейт.

В таблицу намеренно включены формы, которые валидация обязана отбивать: не
абсолютный префикс (`'ru'`), хвостовой слеш, двойной слеш, пустая строка,
запрос, сегмент `.`, два локали на один префикс, коллизия с дефолтным префиксом
другой локали, неподдерживаемый ключ. Тест № 7 отдельно фиксирует диагностику
коллизии — `Duplicate locale prefix: /en` — потому что именно ради неё проверка
коллизий и писалась.

**Это отрицательный результат.** Пара держится; теперь она закреплена, и правка
`normalizeLocalePrefix` или сортировки «длинный префикс раньше» уронит тест.

## 5. V21-03. Поправка к V20 §9

Пункт 5 раздела 9 отчёта V20 предлагал обобщить фаззинг на пары
«`readCatalogsByLocale` против `loadMessages`» и «`buildLocalizeUrl` против
`matchLocalePrefix`». Проверка по коду показала, что оба имени названы зря:

- `buildLocalizeUrl` **не существует**. URL-хелперы в `src/nav-url.ts` называются
  `resolveLocalizedPathname`, `switchLocaleHref` и `rewriteToInternalPath`;
- `loadMessages` — **колбэк из request-конфига** (`src/types.ts:391`,
  `loadMessages?: (locale: string) => Promise<MessageSource> | MessageSource`),
  то есть код, который пишет пользователь. Второй реализацией чтения каталога он
  не является, и сравнивать его с `readCatalogsByLocale` не с чем.

Поправка внесена в текст V20 §9 с пометкой, что она из V21. Зафиксировать это
стоит отдельно: V20 вменял отчёту V19 пометку «недостижимо», написанную без
проверки, — и в том же отчёте появился пункт, написанный по памяти про имена
функций. Правило одинаковое для обоих случаев: имя функции в отчёте — такое же
утверждение о репозитории, как и всё остальное, и проверяется тем же `grep`.

## 6. V21-04. Покрытие стало гейтом

Цифры покрытия в отчётах V15–V20 получались командой, которую никто не
записывал: `node --test --experimental-test-coverage "test/*.test.mjs"`. Ничто
не мешало следующей правке уронить покрытие, и ничто не требовало его
пересчитать.

`scripts/coverage.mjs` запускает набор под репортёром Node с его собственными
порогами — `--test-coverage-lines/-branches/-functions`, — так что решение
принимает раннер, а не разобранный текст, и он же выставляет код возврата:

```
строки 97   ветки 93   функции 96.5
```

Пол намеренно чуть ниже текущего значения (97.34 / 93.48 / 96.80), а не равен
ему: гейт, который приходится править при каждой новой ветке, учит править гейт.
Шаг `Verify coverage floor` добавлен в `ci.yml` после `Run test suite`, скрипт —
в `npm run ci`.

**Проверка самого гейта.** С полом, поднятым до 99.5:

```
[next-fluent] Coverage or the test suite failed (exit 1).
              Floors for dist/: 99.5% lines, 93% branches, 96.5% functions.
exit 1
```

Гейт, который не умеет падать, — не гейт, поэтому проверено и это.

Покрытие считается по `dist/`, как и все цифры в отчётах: собирается то, что
уезжает в пакет, а `check-dist` держит `dist/` в синхроне с `src/`.

### 6.1. V21-05. Что на самом деле мерили отчёты V15–V20

Первая версия гейта сравнивала числа из строки `# all files` и немедленно
упала:

```
[next-fluent] Coverage fell below the floor: functions 95.72% < 96%.
```

Разбор таблицы показал причину: в `# all files` Node усредняет **и тестовые
файлы, и скрипты**, которые их запускают. Худшие строки по функциям выглядели
так:

```
   14.29   test-next-integration.mjs
   61.29   audit-v21.test.mjs
   87.50   audit-v5-coverage.test.mjs
   88.24   next-intl-parity.test.mjs
```

`audit-v21.test.mjs` с 61.29 % — это мой же новый тест: в нём определены
заглушки-колбэки (`rich`, `onError`, `getMessageFallback`, `BRL`, `USD`), которые
по смыслу теста **никогда не вызываются**. То есть цифру «покрытие библиотеки»
двигал харнесс, и двигал в сторону, зависящую от того, сколько заглушек написал
автор теста.

Поэтому отчёт ограничен `dist/` флагом `--test-coverage-include=dist/**`. Числа
меняются содержательно:

```
смешанный отчёт (что мерили V15–V20):  96.84 строки / 93.89 ветки / 95.72 функции
только dist/ (что мерит гейт):         97.34 строки / 93.48 ветки / 96.80 функции
```

Строк и функций в библиотеке больше, чем казалось, а **веток — меньше**:
тестовые файлы почти полностью покрыты по веткам и подтягивали среднее вверх.
Все цифры покрытия в отчётах V15–V20 следует читать как смешанные; пересчёта по
прошлым проходам этот проход не делал.
