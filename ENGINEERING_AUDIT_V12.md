## 1. V12-01 (P2). Код ошибки, которого не бывает

**Воспроизведение.**

```js
import { FluentErrorCode } from 'next-fluent';
console.log(Object.values(FluentErrorCode));
// MISSING_MESSAGE, FORMATTING_ERROR, INVALID_ARGUMENT,
// UNSUPPORTED_VALUE, ENVIRONMENT_FALLBACK
```

```js
// А ведь библиотека это делает — и не говорит об этом:
const less = createFluentBundle('ru', 'greet = Привет\n');
const more = createFluentBundle('ru-RU', '');
const t = createTranslator(more, { onError: (e) => errors.push(e), fallbackBundles: less });
t('greet');  // → 'Привет', errors: 0
```

Ни `bundle.ts`, ни `formatter.ts`, ни `middleware.ts`, ни `check.ts` не содержат
и упоминания `ENVIRONMENT_FALLBACK`: `grep` по `src/` находит два совпадения, и
оба — в самом `errors.ts` (объявление и ветка сообщения). Тестов — ноль.

**Почему это не «убрать на всякий случай».** Приложение пишет
`switch (error.code)` или `if (error.code === …)`, чтобы отправлять ошибки в
свою систему мониторинга. Ветка на несуществующий код там мёртвая, но выглядит
как обработанный случай: человек пишет обработчик «на всякий случай», думая, что
библиотека о таком сообщает.

**Почему не реализовать.** Откат с `ru-RU` на `ru` — это обычная работа
библиотеки, а не неисправность: сообщение найдено и отрисовано. Сообщать об этом
значит объявлять событие на каждом запросе вида `en-GB`, то есть превратить
диагностику в шум. Это была бы новая функциональность, а проход занимается
дефектами; поэтому код удалён, а поведение — тихое и правильное — осталось как
есть.

**Исправление.** `ENVIRONMENT_FALLBACK` удалён из перечисления и из построения
сообщения; ветка `default` в `describe()` сохранена и прокомментирована — код,
пришедший из обычного JavaScript, всё ещё должен дать строку, а не `undefined`.

**Гейт против возврата.** `test/audit-v12.test.mjs` требует, чтобы каждый код из
публичного перечисления (1) имел собственную ветку сообщения и (2) **встречался
в исходниках за пределами `src/errors.ts`**. Второе и есть определение «код,
который библиотека действительно может выдать». Отрицательный контроль: возврат
одной строки в `src/errors.ts` роняет тест.

## 2. V12-02 (P3). Что именно лежит в `cause`

`onError` получает `FluentError`, и в четырёх местах библиотеки к нему
прикрепляется `cause` — два в переводчике, два в `t.attrs()`. Ни одно из них не
было выполнено ни одним тестом, и в README не описана форма.

Проверено пробником и зафиксировано:

| ситуация | `code` | `cause` |
| --- | --- | --- |
| `t('greet')` при `greet = Hi { $name }` | `FORMATTING_ERROR` | `Error[]`, первый — `ReferenceError: Unknown variable: $name` |
| `t('greet', { name: null })` | `INVALID_ARGUMENT` | `{ unsupportedArguments: ['name'], errors: [...] }` |
| `t('greet', { name: { deep: … } })` | `INVALID_ARGUMENT` | то же — значение не превратилось в переменную Fluent |
| `t.attrs('field')` с переменной в атрибуте | `FORMATTING_ERROR` | тот же `Error[]`, а `t.attrs()` возвращает `{}` — разложить нечего, исключения нет |

Само по себе это работало; отсутствовало доказательство и описание. В README
добавлена таблица формы `cause` и оговорка, что `JSON.stringify(error.cause)`
даёт `[{}]`: `message` нативного `Error` не перечисляем, поэтому логировать надо
саму ошибку. Это ровно тот случай, когда человек узнаёт о грабли из продакшена.

## 3. V12-03 (P3). Диагностика парсера и провайдера

**Парсер.** `junkEntries` разбирает непрочитанное на «есть ли в начале строки
`ключ =`». Оказалось, что у значительной части мусора ключа нет: `}`, `= orphan`,
`- item`. Такие записи попадают в отчёт без `id`, и `unparsableCatalogError`
должен назвать вместо ключа сам каталог — иначе сообщение вида
`contains 1 entry …: "}"` осталось бы без указания, о каком файле речь (у него
в `message` входит `context`, так что имя файла там есть, а вот `error.key` был
бы `undefined`). Зафиксированы: запись без ключа не исчезает, ключ у неё
`<catalog>`, единственная запись с ключом называет его, а форма единственного
числа («1 entry») и множественного («2 entries») различается.

**Провайдер.** `FluentServerProvider` отбрасывает функции из
`defaultTranslationValues` — React не умеет сериализовать их через границу
RSC, — и эта ветка не выполнялась ни разу. Покрыта рендером через
`prerender` (компонент асинхронный и suspend'ит, поэтому `renderToStaticMarkup`
для него не годится): функция в конфиге не ломает дерево, обычные значения
рядом с ней доходят до сообщений. Второй рендер — без `defaultTranslationValues`
вовсе — закрывает противоположную сторону тернарника.

## 4. О чём этот проход НЕ трогал

`client.js` (70.2 % ветвей) и `navigation.js` (59.5 %) остались нетронутыми
осознанно, и это не откладывание:

- `navigation.js` — непокрыты `back()`, `forward()`, `refresh()` и обёртка
  `LocalizedLink`. Это делегаты, работающие только внутри контекста App Router.
  В Node их нечем накрыть; браузерные прогоны CI недоступны локально, а писать
  тест, который нельзя выполнить, — значит записать обещание.
- `client.js` — оставшиеся ветви живут в `useEffect`/`useMemo`, которые
  `renderToStaticMarkup` не выполняет.

Причина одна: покрытие таких строк даёт число, а не уверенность. Хвост
закрывать буду там, где его можно закрыть доказательством.

## 6. Приоритеты следующего прохода

1. **`LocalizedLink` (0 тестов).** Единственный клиентский экспорт без единого
   теста. Проверять его — в браузерных прогонах CI, где App Router есть, а не
   в Node, где его нет.
2. **`usage.js`, 88.0 % ветвей.** Самый густой участок кода в библиотеке и
   самый склонный к тихим ошибкам: разбирать построчно, а не по покрытию.
3. **`client.js`.** Браузерный контур: `useNow({ updateInterval })`,
   `useFormatter` при смене локали. Ни то, ни другое нельзя проверить в Node —
   значит, проверять в CI или не браться.
4. **`check.ts` / `pseudo.ts`.** Обе команды CLI работают, но покрыты по
   счастливым путям; V10 показал, где именно там бывают сюрпризы.
