## 2. P1 — потеря сообщений в клиентском payload (исправлено)

### V5-01. `pickMessages` вырезал сообщения, на которые ссылается namespace (исправлено)

**Что не так.** `pickMessages(source, namespace)` отбирал сообщения по префиксу
namespace и дополнительно собирал только **термины** (`-brand`), на которые
отобранные сообщения ссылаются. Ссылка на *сообщение* (`{ common-greeting }`)
не отслеживалась, хотя это ровно такая же часть смысла: без адресата
плейсхолдер не разрешается.

**Почему это важно.** Это документированный сценарий передачи клиентскому
компоненту только нужного namespace. В браузере сообщение рендерится как
собственный ключ, а `FORMATTING_ERROR: Unknown message` уходит в `onError` —
то есть пользователь видит `checkout-title` вместо текста.

**Воспроизведение** (каталог из README-примера):

```js
const catalog = `
-brand = Acme
common-greeting = Hello from { -brand }
checkout-title = Buy { common-greeting }
other-title = Other
`;
pickMessages(catalog, 'checkout');
```

| | |
| --- | --- |
| До | `checkout-title = Buy { common-greeting }` — `common-greeting` вырезан<br>`t('checkout-title')` → `"checkout-title"`, `onError`: `FORMATTING_ERROR ... Unknown message` |
| После | `-brand = Acme` + `common-greeting = Hello from { -brand }` + `checkout-title = Buy { common-greeting }`<br>`t('checkout-title')` → `"Buy Hello from Acme"` |

**Исправление.** `src/pick-messages.ts`: сборщик ссылок теперь `Visitor` с
`visitTermReference` **и** `visitMessageReference`; отбор идёт обходом в ширину
от сообщений namespace — каждая ссылка (сообщение или термин) добавляется в
набор и ставится в очередь, поэтому цепочки `message → message → term`
разрешаются полностью. Вывод сохраняет исходный порядок каталога, каждый
объект печатается один раз (self-reference `ns-a = A { ns-a }` больше не
дублирует строку). `keepTerms: false` по-прежнему оставляет термины за бортом,
но не трогает ссылки на сообщения: без них отобранный каталог нерабочий.

**Тесты:** `test/audit-v6.test.mjs`, 6 кейсов V5-01 (включая транзитивность и
порядок).

## 3. P2 — артефакты собирались из неполного или противоречивого каталога (исправлено)

Общее свойство этих трёх находок: инструменты (`typegen`, `pseudo`,
`pickMessages`, JSON-конвертер) не проверяли вход и выдавали результат, по
которому невозможно понять, что часть каталога потеряна или переопределена.
`check` при этом сообщал о проблеме — расхождение между проверкой и сборкой.

### V5-02. Два разных JSON-ключа давали один Fluent-id (исправлено)

**Что не так.** Конвертер JSON→FTL отображает `{"nav-home": …}` и
`{"nav": {"home": …}}` в один и тот же id `nav-home`, но коллизию не
обнаруживал.

**Воспроизведение.**

```js
jsonToFluent({ 'nav-home': 'A', nav: { home: 'B' } });
// до:   'nav-home = A\nnav-home = B\n'
// после: FluentError INVALID_ARGUMENT: JSON catalog keys "nav-home" and
//        "nav.home" both map to the Fluent message id "nav-home".
```

Последствия до правки: `addResource` в рантайме печатает `console.warn` и
оставляет **последнее** определение (первый перевод пропадает), а `typegen`
молча генерирует один ключ — то есть `t('nav.home')` и `typegen` расходятся.
Та же коллизия бывает глубокой: `{a: {'b-c': …}, 'a-b': {c: …}}` → `a-b-c`
дважды, и между написаниями одного ключа: `{'a-b': …, 'a.b': …}`.

**Исправление.** `src/catalog.ts`: `walk` прокидывает карту «id → JSON-путь»;
повтор id с другим путём — `FluentError(INVALID_ARGUMENT)` с обоими путями.
Атрибуты (`id.attr`) под проверку не попадают: у них id уникален по
построению.

**Тесты:** 4 кейса V5-02 (включая вложенную коллизию и отрицательный — два
разных ключа конвертируются как раньше).

### V5-03. Нечитаемые записи (`Junk`) молча исчезали из артефактов (исправлено)

**Что не так.** Парсер `@fluent/syntax` не бросает исключение на битое
сообщение: он складывает текст в узел `Junk` и возвращает ресурс **без** этого
сообщения. `check` такие узлы видит (`parse-error`), а `typegen`, `pseudo` и
`pickMessages` — нет: они обходили `resource.body`, пропуская `Junk`, а
`FluentSerializer` по умолчанию (`withJunk: false`) его не печатает.

**Воспроизведение.**

```js
pseudoLocalizeFtl('good = Fine\nbad = Broken { unclosed\n');
// до:   'good = [Ƒîîñéé]\n' — сообщения bad просто нет
// после: FluentError INVALID_ARGUMENT: The catalog contains 1 entry the Fluent
//        parser cannot read: "bad = Broken { unclosed"
```

`extractMessagesFromFtl` вёл себя так же: сломанное сообщение не попадало в
.declarations, и `t('bad')` падало «not a known key» вместо указания на каталог.

**Исправление.** Общий помощник `junkEntries()` + `unparsableCatalogError()` в
`src/ftl-parse.ts` (первая строка каждой нечитаемой записи + её id, если он
разбирается):

- `typegen` (`extractMessagesFromFtl`) и `pseudoLocalizeFtl` — бросают
  `FluentError` на любой `Junk`: генератор не имеет права выдавать неполный
  артефакт;
- `pickMessages` — бросает только если нечитаемая запись принадлежит
  запрошенному namespace (junk чужих namespace вырезается по плану);
- `listMessageKeys` по-прежнему перечисляет только разобранные записи — это
  «какие ключи есть», а диагноз даёт `check` (это осознанное разделение, см.
  §6).

**Тесты:** 4 кейса V5-03 (включая «читаемый каталог не затронут»).

### V5-04. Литеральные фигурные скобки было нечем выразить в JSON (исправлено)

**Что не так.** `{count}` и `{$count}` намеренно становятся переменными
(совместимость с ICU/next-intl), но отступной формы для **литеральных** скобок
не существовало. `"has {braces}"` превращалось в `{ $braces }`, форматирование
падало, и сообщение рендерилось своим ключом:

```js
jsonToFluent({ b: 'has {braces}' });   // 'b = { "has " }{ $braces }'
t('b');                                // "b" + FORMATTING_ERROR: Unknown variable
```

Текст вроде `Braces { and } here` (пробелы внутри) работал, поэтому проблема
проявлялась только на одиночных словах в скобках — то есть незаметно.

**Исправление.** `\{` и `\}` в любом JSON-значении теперь означают литеральную
скобку; регэксп разбора расширен до `\\[{}]|\{\$?…\}` и в цикле
`renderInline` экранированный символ печатается как строковый плейсхолдер:

```js
jsonToFluent({ b: 'has \\{braces\\}' });
// 'b = { "has " }{ "{" }{ "braces" }{ "}" }'  →  t('b') === 'has {braces}'
```

Обычные переменные (`{name}`, `{count}`, `{$name}`) и текст с пробелами внутри
скобок работают как раньше. README дополнен разделом про escape.

**Тесты:** 2 кейса V5-04.

## 4. P3 — исправлено

### V5-05. `Accept-Language: en;q=0,*` согласовывал английский (исправлено)

**Что не так.** RFC 9110 §12.5.4: `q=0` — это «неприемлемо». Код отбрасывал
такие записи, но ветка `*` выбирала предпочтительную локаль (`preferred`) или
`locales[0]`, не глядя на отказы.

```js
resolveAcceptLanguage('en;q=0,*',  ['en','ru'], 'en');  // до: 'en'   после: 'ru'
resolveAcceptLanguage('*,en;q=0',  ['en','ru'], 'en');  // до: 'en'   после: 'ru'
resolveAcceptLanguage('en;q=0,ru;q=0,*', ['en','ru'], 'en'); // после: undefined
```

**Исправление.** `src/utils.ts`: разбор возвращает запись и с `q=0`; она
попадает в набор «отказано» (ленивый `Set` — на обычном заголовке аллокаций
нет). Решение по `*` откладывается до конца разбора, поэтому отказ действует
независимо от того, стоит он до или после звёздочки. Обычный путь (сортировка
по q, первый при равенстве) не изменился — есть регрессионные тесты.

**Тесты:** 4 кейса V5-05.

### V5-07. Анализатор использования падал на глубокой вложенности (исправлено)

`src/usage.ts` (`indexCatalog`) парсил сырым `parse()`, тогда как все остальные
потребители — через `parseFtl()`. Каталог с несколькими тысячами вложенных
плейсхолдеров давал `RangeError: Maximum call stack size exceeded` внутри
`check --usage` вместо адресной ошибки. Теперь используется `parseFtl`:
`FluentError: The catalog is nested too deeply for the FTL parser`.

### V5-08. `maskNonCode` съедал перенос строки после `\` (исправлено)

Маскируя не-код, анализатор заменял пробелами и обратный слэш, и следующий
символ — включая `\n` шаблонной строки с продолжением. Все последующие
диагностики в файле сдвигались на строку вверх:

```ts
const t = useTranslations("ns");
const text = `first\
second`;
t('ns-missing');
```

| | |
| --- | --- |
| До | `missing` на строке **3** (и содержимое следующей строки склеено) |
| После | строка **4** |

**Исправление.** Перенос строки сохраняется; пробелом закрывается только
экранируемый символ, если это не `\n`.

**Тесты:** 2 кейса V5-08 (второй — что `\`` и другие escape по-прежнему
маскируются).

### V5-09. Абсолютная форма Host (`example.com.`) не распознавалась (исправлено)

Хост с точкой на конце — легитимная FQDN-форма того же хоста (её шлют
некоторые клиенты, health-check'и и прокси). Сравнения шли по строкам, поэтому
такой запрос получал **421** при настроенном `trustedHosts`, а домен-роутинг
для него молча не применялся:

| Запрос | До | После |
| --- | --- | --- |
| `Host: example.com.` + `trustedHosts: ['example.com']` | `421` | `200` |
| `Host: example.com.` + `domains: [{domain:'example.com'}]`, путь `/ru/docs` | `200`, rewrite нет | `307 → https://example.ru/docs` (как и без точки) |

**Исправление.** `normalizeHostForMatching()` в `src/middleware.ts`
(в `hostMatchesTrustedList`, при сравнении `x-forwarded-host` с `Host` и для
`requestHost`) и `normalizeHost()` в `src/domain-routing.ts` (`findDomain`).
В `Link`/`Location` хост остаётся таким, каким его прислал клиент, —
нормализация касается только сопоставления.

**Тесты:** 2 кейса V5-09 (allow-list + полная эквивалентность ответов для
точечной и обычной записи, включая кросс-доменный редирект).

### V5-13. Поведение `useNow()` без `now` в конфиге не было описано (исправлено)

`useNow()` на сервере отдаёт эпоху (`1970-01-01T00:00:00Z`) и переключается на
живые часы после монтирования — так задумано (комментарий `STATIC_NOW` в
`src/client.ts`: иначе SSR и клиент не совпадут при гидратации), и с
`FluentServerProvider`/`now` в request-конфиге серверный HTML сразу содержит
момент запроса. Но README об этом молчал, а «1970» в SSR-разметке выглядит как
баг.

**Исправление:** раздел «Client Components» README явно описывает правило и
говорит, когда нужно передать `now`. Кода это не меняет — поведение
корректное, изменилась только документация.

## 5. P3 — закрыто во втором заходе (V5-06, V5-10, V5-11, V5-12)

### V5-06. `typegen` расходился с рантаймом на перекрытом атрибуте (исправлено)

Разрешение ключей (`buildKeyCandidates` в `src/utils.ts`) проверяет
**дефисную** форму раньше прямой — это нужно, чтобы `t('nav.home')` находил
сообщение `nav-home` из JSON-каталога. Следствие: если в каталоге есть и
сообщение `greeting-formal`, и атрибут `.formal` у сообщения `greeting`,
`t('greeting.formal')` форматирует **сообщение**, а `typegen` объявлял для
этого ключа аргументы атрибута (`{ name }` вместо `{ nick }`) — типы
отправляли вызывающий код ровно по неверному пути, и вызов рендерился ключом.

```ftl
greeting =
    .formal = Good day, { $name }
greeting-formal = Hey { $nick }
```

| | |
| --- | --- |
| До | `'greeting.formal': { 'name': … }` — рантайм же требует `nick`: `t('greeting.formal', { name: 'Ada' })` → `FORMATTING_ERROR`, ключ |
| После | `'greeting.formal': { 'nick': … }` + комментарий в сгенерированном файле: ключ разрешается в сообщение `greeting-formal`, атрибут доступен только через `t.attrs('greeting').formal` |

**Исправление.** `src/typegen.ts`: `generateTypeDeclarations` строит карты
`valueById` (сообщения со значением) и `attributesById` и для каждого
объявляемого ключа повторяет разрешение рантайма — кандидаты «дефисная форма,
сам ключ», каждый сначала как id сообщения, затем как путь `id.attr`. Аргументы
берутся у победителя; для перекрытых атрибутов в файл печатается поясняющий
комментарий. Поведение рантайма не менялось — менялись только объявления и
README (порядок разрешения описан в таблице JSON→FTL).

**Тесты:** 4 кейса V5-06, включая сверку объявленного имени переменной с тем,
что реально форматирует `createTranslator` на том же каталоге.

### V5-10. Публичный URL из непроверенного `Host`: предупреждение и loopback (исправлено)

Две отдельные проблемы вокруг `x-forwarded-host`/`Host`:

1. Предупреждение V4-09 срабатывало только там, где middleware сам выпускает
   редирект. Ответ 200 с `Link: <https://<host>/…>; rel="alternate"` строился
   из того же непроверенного `Host` молча.
2. `x-forwarded-host: localhost:3000` считался доверенным **безусловно**, даже
   если `Host` — публичный домен. Клиент мог одним заголовком увести
   `Location`/`Link` на `localhost` (при незаданном `trustedHosts` — вплоть до
   отравления общего кеша ответом с `localhost`-ссылками).

**Исправление.** `src/middleware.ts`:

- предупреждение (dev, один раз на процесс) теперь вызывается и при выпуске
  alternate-ссылок, и его текст говорит про оба публичных URL — `Location` и
  `Link`; в production не печатается;
- loopback-исключение требует, чтобы **и соединение** пришло с loopback
  (`Host` тоже `localhost`/`127.0.0.1`/`[::1]`): локальный dev-прокси работает
  как раньше, а публичный запрос с подделанным заголовком больше не влияет на
  origin.

| Сценарий | До | После |
| --- | --- | --- |
| `Host: example.com` + `x-forwarded-host: localhost:3000` | `Link` → `https://localhost:3000/…` | `Link` → `https://example.com/…` |
| `Host: 127.0.0.1:3000` + `x-forwarded-host: localhost:3000` | доверенно | доверенно (loopback-прокси) |
| 200 с `Link` без `trustedHosts` (dev) | тишина | предупреждение |

**Тесты:** 3 кейса V5-10, включая запуск middleware отдельным процессом в
`NODE_ENV=development`/`production` для проверки самого предупреждения.

### V5-11. Cookie при `localeDetection: false` (исправлено)

```js
createI18nMiddleware({ …, localeDetection: false })(request('/'))
// до:    Set-Cookie: NEXT_LOCALE=en; …
// после: без Set-Cookie
```

Cookie никто не читал обратно (`cookieLocale` вычисляется только при
включённой детекции), поэтому значение по умолчанию лишь делало документ
некешируемым. Теперь cookie не пишется, **если конфиг `localeCookie` не задан
явно**: `localeCookie: { … }` остаётся осознанным opt-in (например, чтобы
`getLocale()` работал на маршрутах вне matcher'а), `localeCookie: false` —
как и раньше. Поведение описано в README рядом с абзацем про cookie.

**Тесты:** 3 кейса V5-11 (детекция включена — cookie есть; выключена — нет;
явный конфиг — есть).

### V5-12. Wildcard в `trustedHosts` матчил апекс (исправлено)

```
trustedHosts: ['*.example.org']
до:    example.org → 200, a.example.org → 200
после: example.org → 421, a.example.org → 200
```

«Мягкая» трактовка `*.` удобна для «www + apex», но allow-list, тихо
принимающий хост, которого оператор не записывал, — неверный дефолт для
контроля, чья задача отвергать чужие `Host`. Теперь `*.example.org` — только
подуровни (как в сертификатах), апекс перечисляется явно:
`['example.org', '*.example.org']` — ровно та форма, что стоит в README-примере.
Семантика зафиксирована в SECURITY.md и README, изменение перечислено в
CHANGELOG (breaking-пункт для тех, кто полагался на старое поведение).

**Тесты:** 2 кейса V5-12 (только wildcard → апекс 421; апекс + wildcard → оба 200).

## 6. Что проверено и оказалось в порядке

Список того, что целенаправленно атаковалось и устояло (перечитывать перед
следующим проходом, чтобы не искать то же дважды):

- **URL/навигация.** 27 кейсов `getPathname`/`Link`/`getPathname`+`Link`+router:
  объектный `href` (query-строка, массив, hash, встроенный `?#`), `basePath`
  (strip/add/корень), вычистка `params` из query, `forcePrefix`, кросс-домен →
  абсолютный URL, hash-only и `mailto`. `//evil.example/x` и `////evil.example/x`
  остаются внешними (не превращаются в путь), `\` нормализуется в `/`,
  `ftp:`/`javascript:` отвергаются («Unsupported URL object protocol»),
  неизвестная локаль не падает. Сверка middleware ↔ `resolveLocalizedPathname`
  на 8 конфигурациях × наборе href — **0 расхождений**.
- **Middleware.** Матрица опций: `localeCookie: false`, `localeDetection: false`,
  `alternateLinks: false`, кастомные `cookieName`/`headerName`/`prefixes`,
  домены с чужим префиксом (307 и обратно, порт сохраняется), 421 на внешний
  `Host`, `Vary` строго на detection-ответах, cookie только на document-навигацию
  и только при смене значения, `Secure` в production; при `localeDetection:
  false` cookie по умолчанию не пишется вовсе (V5-11). Имитация цикла
  «переписывание → повторный заход» на **реальном Next 15** цикла не даёт:
  сигнальные заголовки `x-next-fluent-rewrite`/`-token` middleware добавляет
  сам, а клиентские копии удаляет; цикл воспроизводился только в моке без
  этих заголовков (артефакт харнесса, не дефект).
- **`x-forwarded-host`.** Доверяется только если совпадает с `Host`, с
  настроенным доменом или если **и заголовок, и соединение** — loopback
  (V5-10); `evil.test` не влияет ни на `Location`, ни на `Link`; при
  `trustedHosts` — 421. Прокси-сценарий из `test:next:domains` (`Host` и
  `x-forwarded-host` одного публичного домена за TLS-терминатором)
  воспроизведён unit-пробником: кросс-доменный редирект и alternate-ссылки
  строятся от публичного домена, не от `127.0.0.1`.
- **Переводчик.** `t`/`attrs`/`raw`/`plain`/`rich`/`has` на сообщениях без
  атрибутов, без значения и отсутствующих: `MISSING_MESSAGE` без падений,
  `has('attr-only') === false`, `has('attr-only.title') === true`;
  `Date`, `bigint` (без потери разрядов), `bool`, `null`/`undefined`
  (`INVALID_ARGUMENT` и возврат ключа), объекты; `raw()` отдаёт массив строк,
  `rich()` без значений возвращает строку как есть.
- **JSON-каталоги.** Массивы/`null`/`undefined`/не-plain-объекты/слишком
  глубокая вложенность отклоняются адресно; кавычки, обратные слэши, переводы
  строк, padding, пустые значения и атрибуты round-trip'ятся побайтово
  (`useIsolating` не мешает, изоляты снимаются в `attrs`/`raw`); `isJsonCatalog`
  не путает `FluentBundle` с объектом.
- **Pseudo-локаль.** 17 адверсариальных FTL (ведущие `[`, `.`, `*`, `{`,
  многострочные значения, `select`, термины, юникод) — round-trip без потерь;
  Junk теперь отклоняется (V5-03).
- **Запросный scope.** `setRequestLocale` вне request scope бросает
  `FluentError`; `getLocale()` вне Next отдаёт `'en'`;
  `getRequestConfigSnapshot('ru')` → `{ locale: 'ru', messages: '', timeZone: 'UTC', now }`.
- **CLI.** `check` возвращает 1 на missing-keys и на `--strict-usage`;
  `--input <файл>` и `--reference <чужой локаль>` дают адресные ошибки;
  `--json` печатает машиночитаемый отчёт; `typegen` идемпотентен (второй запуск
  пишет «already up to date»).
- **`t()`-контракт с `{...}`.** Интент ICU-подобных подстановок (`{name}` →
  `{ $name }`) сохранён, включая `{ and }` с пробелами — это по-прежнему
  литеральный текст (V5-04 добавил только escape-форму).
- **Конкурентные запросы в живом Next.** `Promise.all` по `/`, `/ru`, `/live`,
  `/ru/live` (layout с `setRequestLocale` + страница с `getLocale()`, плюс
  динамический маршрут с заголовком) — каждый ответ несёт свою локаль на
  Next 15.5.26 и Next 16.4.0: ни request-scope, ни кеш бандлов не протекают
  между рендерами (закрывает хвост V4-16).
- **Гигиена.** `npm audit --omit=dev` и полный — 0 уязвимостей; `dist/`
  воспроизводится из `src/`; `files` в `package.json` совпадает с фактическими
  точками входа (все 16 подпутей резолвятся в `test:consumer`).
- **Известные ограничения, зафиксированные как замысел (не дефекты):**
  `useNow()` без `now` = эпоха на сервере (V5-13 — описано в README);
  rewrite всегда на origin `request.url`, публичные URL — на `Host`
  (комментарий в коде + тест «Rewrites intentionally stay on request.url's
  origin»); `t('user.name')` предпочитает сообщение `user-name`
  (V5-06 — исправлено на уровне типов и комментария, само правило не
  менялось).

## 8. Приоритеты для следующего прохода

Открытых дефектов прохода V5 нет; CI-матрица (8/8, включая браузерные
прогоны) на PR #7 зелёная. Что стоит сделать дальше:

1. **Бюджет клиентского бандла.** `dist/index-browser.js` — точка входа
   бандла, поэтому его реэкспорты не выкидываются tree-shaking'ом и в клиент
   попадают `resolveAcceptLanguage` и `jsonToFluent` целиком. Запас — 0.2 kB
   min / 0.3 kB gzip (16.2 из 16.5 gzip на корневом энтри), то есть любая
   следующая правка клиентского графа либо ужмёт его, либо потребует осознанно
   поднять бюджет, либо сузить публичную поверхность корневого энтри
   (API-решение, поэтому не сделано в этом проходе).
2. **V5-06 как симптом.** Перекрытие «сообщение `a-b` против атрибута `a.b`»
   теперь корректно описано типами и комментарием, но сам атрибут по-прежнему
   недостижим через `t()` (только `t.attrs()`). Если это когда-нибудь станет
   проблемой, правило разрешения в `buildKeyCandidates` придётся пересматривать
   вместе с форматом ключей JSON-каталогов.
3. **Расширять адверсариальные пробники** по мере роста: в этом проходе
   самыми продуктивными были попытки ответить на вопрос «какой артефакт
   получится, если каталог частично битый/противоречивый» — стоит продолжать
   систематически (junk, дубликаты, коллизии id, атрибуты без значения).
4. **Проверить workflow публикации вживую** — `publish.yml` написан, но ни
   один релиз через него ещё не проходил; первый dry-run (`workflow_dispatch`
   с `dry-run: true`) подтвердит, что гейт и аутентификация настроены.
