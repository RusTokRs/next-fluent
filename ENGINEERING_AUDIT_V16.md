## 1. V16-01 (P1). `trustedHosts` выключался одним заголовком

`x-forwarded-host` — заголовок запроса, то есть его полностью контролирует
клиент. Ветка, которая доверяет forwarded host «потому что он совпадает с
настроенным доменом», существует для прокси, который не переписывает `Host`.
Но `trustedHosts` проверялся **после** подстановки — то есть против хоста,
который выбрал клиент.

Воспроизведение (`trustedHosts: ['example.com', 'shop.example.com']`,
настроены оба домена):

| `Host` | `x-forwarded-host` | до правки |
| --- | --- | --- |
| `evil.com` | — | **421** |
| `evil.com` | `example.com` | **307 → `https://example.com/ru/about`** |
| `evil.com` | `shop.example.com` | **307 → `https://shop.example.com/ru/about`** |

Ровно тот инвариант, ради которого контроль написан («Misdirected/foreign
Host: never emit redirects that a poisoned cache could replay on the real
origin»), снимался одним заголовком: 421 решался против attacker-chosen хоста и
проходил.

**Правка.** Доверять forwarded host «по домену» можно только когда хост, на
который запрос действительно пришёл, сам доверенный:

```ts
domains?.some((item) => /* … */) &&
  (trustedHosts === undefined || trustedHosts.length === 0 ||
    (directHost !== null && hostMatchesTrustedList(directHost, trustedHosts)))
```

Что это ломает и что нет, проверено отдельно:

* без `trustedHosts`allow-листа нет — ветка работает как раньше, прокси без
  переписывания `Host` по-прежнему обслуживается (это зафиксировано тестом в
  `domain-prefixes.test.mjs`, тест зелёный);
* `Host: example.com` + `x-forwarded-host: example.com` при
  `trustedHosts: ['example.com']` — настоящий прокси, работает;
* развёртывание, где `Host` внутренний и `trustedHosts` задан, **и раньше**
  отвечало 421 на всё (проверено замером до правки), то есть регрессии нет.

## 2. V16-02 (P1). `Host: example.com:443` — тот же авторитет, но 421

Проверка «заголовок должен пережить парсер без изменений» ловит настоящий
подвох: `Host: a.test/b` парсится в host `a.test`. Единственное отличие, которое
не является другим авторитетом, — порт по умолчанию для схемы, который парсер
**отбрасывает**: `new URL('https://example.com:443').host === 'example.com'`.

Из-за этого сравнение не проходило, хост не подставлялся, и при
`trustedHosts: ['example.com']`:

```
Host: example.com        => 200
Host: example.com:443    => 421   ← собственный домен сайта
Host: example.com:80     => 200   ← другой порт, но тот же домен
Host: example.com:8443   => 200
```

Один и тот же домен принимается или отвергается в зависимости от того, оказался
ли порт портом по умолчанию для схемы. Сайт гаснет (421 — не редирект, а
отказ) для клиентов, которые пишут порт явно, а это делают и health-чеки, и
часть прокси.

**Правка.** Дополнительно принимается ровно одна форма — `<hostname>:<default
port>` при условии, что парсер отбросил порт (`parsedHost.port === ''`), то есть
hostname совпадает дословно и подменить другой авторитет нечем:

```ts
const sameAuthority =
  parsedHost.host === rawHost.toLowerCase() ||
  (parsedHost.port === '' &&
    rawHost.toLowerCase() === `${parsedHost.hostname.toLowerCase()}:${defaultPort}`);
```

Проверено, что не перестало работать: `example.com:8443`, `example.com:80`
(allow-лист сверяет имя хоста, порт в имя не входит — это его прежнее
поведение), `example.com:443:80`, `example.com@evil.com`, `example.com.evil.com`
по-прежнему дают 421.

## 3. V16-03 (P2). `prefetch` не делал ничего на однодоменном сайте

```ts
if (options?.locale && domainLocalePrefix(
  locales, config.localePrefix, findLocaleDomain(config.domains, options.locale)
).mode !== 'always') return;
```

Правило про домены применялось и когда `domains` не настроен вовсе. Тогда
`findLocaleDomain` возвращает `undefined`, `domainLocalePrefix` откатывается на
глобальный префикс — и условие вырождается в «глобальный режим не `always`».
На обычном однодоменном сайте в `as-needed` (дефолтная форма) переключатель
языка не префетчил ничего:

| режим | `prefetch('/about', { locale: 'ru' })` до правки |
| --- | --- |
| `as-needed` | — |
| `never` | — |
| `always` | `/ru/about` |

`/ru/about` — ровно тот URL, ради которого prefetch и вызывали.

**Правка.** Правило теперь действует только когда домены действительно
настроены:

```ts
if (options?.locale && config.domains) {
  const domain = findLocaleDomain(config.domains, options.locale);
  if (domain && domainLocalePrefix(locales, config.localePrefix, domain).mode !== 'always') return;
}
```

Промежуточная версия правки (пропускать «внешние» цели через `isExternalUrl`)
была отвергнута замером: она ломала доменный случай с режимом `always`, где
абсолютный URL цели — норма. Первая, более узкая правка ничего не ломает.

## 4. V16-04. Инвариант-гейт вместо точечных тестов

Все три находки — расхождения между двумя слоями, которые считаются
согласованными. Вместо очередной таблицы «случай × ожидание» добавлен гейт:
**каждый URL, который выдаёт навигация, middleware уже считает каноническим**
(иначе отрендеренный `<Link>` стоит редиректа на каждом клике).

Прогоняется по 8 конфигурациям (режимы префикса, `basePath`, домены с
переопределением режима, локализованные слаги, catch-all, динамические
маршруты) × локали × 5 маршрутов. Стенд моделирует реальный контракт Next:
`nextUrl.pathname` не содержит `basePath`, `nextUrl.basePath` отдельное поле.

Этот стенд заодно поймал две собственные ошибки проверки в этом проходе: сначала
он передавал `basePath` и внутри `pathname`, и отдельным полем (противоречие),
затем абсолютный URL с basePath — в обоих случаях «дефектом» оказывался стенд,
а не библиотека. Это записано здесь, потому что повторение такой ошибки —
привычное дело: она выглядит как настоящая находка.

## 5. Что проверено и оказалось в порядке

**Кэширующий CDN.** §6 V16 обещал этот сценарий; он не дал дефекта.
`Vary: Accept-Language, Cookie` ставится ровно на тех ответах, где решение
приняла детекция, и не ставится там, где локаль пришла из URL. Проверено
перебором режимов × (префикс в URL / без префикса) × (cookie / Accept-Language /
ничего) — 18 сочетаний, ни одного расхождения. Отдельно проверено, что
`Set-Cookie` на URL-производных ответах безопасен для кэша: его значение всегда
равно локали из URL, поэтому переигровка кэшем не может приписать посетителю
чужую локаль.

**`basePath` в сочетании с доменами.** 10 комбинаций (разделённый и встроенный
`basePath`, локаль текущего домена, локаль чужого домена, корень) — редиректы
и переходы между доменами сохраняют `basePath`, лишних префиксов нет.

**Два независимых Next-приложения за одним reverse proxy.** Общий дефект
(`NEXT_LOCALE` у обоих приложений, `path: /`) — это свойство развёртывания, а
не библиотеки: имя и `path` настраиваются через `cookieName` и `localeCookie`.

   крупный непокрытый блок в `src/`. Он исполняется только внутри request scope,
   который в песочнице воспроизводится harness'ем; V10 §3 закрыл настоящий

   строки: V8 закрывал безопасность разметки, с тех пор частота проходов заметно
   выросла.

   Прежнее решение V15 §4 остаётся в силе: без решения владельца по `jsdom` или
   браузерному гейту это не закрывается, и выдавать за находку нельзя.
4. **`Link` header на редиректах.** `createRedirect` не добавляет alternates —
   это осознанно (редирект канонизирует, SEO-важна цель), но стоит проверить,
   не теряется ли `x-default` при связке с `pathnames` и доменами.
